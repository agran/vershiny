# Код-ревью 2026-08-20 — невнедрённые позиции

Всё, что ревью 2026-08-20 (`BUG-1…5`, `P1…P8`) и оба аудита производительности
(2026-08-18 и 2026-08-19) предлагали и что внедрено, описано в
[STATUS.md](STATUS.md) — «Решённые проблемы» и «Производительность». Этот файл
хранит только невнедрённое и сознательно отклонённое.

## Не внедрено

### Марш — условная `normalizeLon` (средний выигрыш, побитово)

`makeRayMarcher` на каждом из ~1.9 млн шагов панорамы гоняет двойной `%`
через `normalizeLon`, хотя `lon1 ∈ [−180, 180)` и `atan2 ∈ (−π, π]` дают
`|lon2| < 360`. Замена на

```ts
if (x > 180) x -= 360; else if (x < -180) x += 360;
```

даёт **побитово тот же результат** и −15–25 % от 103 мс/панораму (замер
аудита). Паритет с `destination` уже стережёт тест в `geo.test.ts`.

### Офлайн — обрезка лучей по bbox патча (средний выигрыш)

В офлайне с патчем региона лучи за bbox дают NaN на **всех** оставшихся
шагах (Terrarium недоступен, грубая пирамида не тянется при fineAtOrigin).
Долгота вдоль луча постоянного азимута монотонна, широта имеет не более
одного экстремума → пересечение луча с lat/lon-bbox — 2–3 интервала.
Последний шаг внутри bbox находится грубым проходом (16–32 точки на луч,
~115 тыс. `destination` ≈ 6 мс) с локальным уточнением. Экономия в чистом
офлайн-патче — **~64 % шагов** (дальняя зона 30–200 км). Нужен тест
«профиль бит-в-бит не изменился» на реальных DEM-тайлах.

### Рендер (низкий приоритет — горячие пути закрыты кэшами сцены и AR-оверлея)

- **Предрасчёт геометрии гребней в ray-index** (аудит №2.4): флаги «выше
  runningMax + EPS» и разрывы не зависят от view; в кадре проход только по
  видимым индексам (≈ 1/5 лучей). Сейчас `buildRidgeSegments` строится на
  каждый прямой рендер.
- **Кэш `uiScale`** (№2.6): `ctx.canvas.clientWidth` — layout-read на кадр;
  кешировать в `resize()`.

### Старт — peaks-парс в воркер (опция)

`peaks/iberia.json` (4.84 МБ, 49 тыс. вершин) парсится на главном потоке.
Двухфазный старт и кеш изоляции уже смягчают, но `JSON.parse` остаётся.

### Холодный декод — `quant` в `cell()`

`decodeTile` предумножает 65 536 значений на `quant` при каждом декоде
(~5.2 млн операций на холодный расчёт). Перенос в чтение
(`tile[i] * quant` в `cell()`) — в 16 384 раза меньше умножений; int16×int
точна для высот до 32 767 м. −5–15 мс холодного старта.

### Service Worker — таймауты в стратегиях

`networkFirst` для `peaks/*.json` и кеш-стратегии тайлов вызывают `fetch`
без таймаута: при «мёртвой» сети соединения держатся до TCP-таймаута ОС.
Клиентский abort распространяется, но стоит добавить `AbortSignal.timeout`.

### Мелочи (опционально)

- Числовой ключ тайла `(z << 16) ^ (x << 10) ^ y` вместо строки `z/x/y`
  (частично покрыто кешем последнего тайла).
- Слияние quant- и delta-проходов `decodeTile` (побитово, −30 % декода).
- `smoothLayers` — скользящее окно вместо `%` по кольцу (2–5 мс десктоп).

## Осознанно отклонено

- **Батч-предфильтр пиков 2°** (Claude №2Б): меняет `hiddenDeficitM` и
  классы на границе — «визуально», не побитово; выгода ~15–25 мс не оправдывает.
- **Прореживание prefetch-веера по зуму** (Claude №4Б): шаг веера привязан
  к тайлу z10 — прореживание ломает покрытие. Безопасный вариант
  (coverage-aware отказ от грубых LOD) внедрён.
- **Перестановка арифметики в `pointAt`** (−10–20 %): ломает побитовый
  паритет `makeRayMarcher` с `destination` — инвариант дороже прироста.
- **Декодированные тайлы в IndexedDB вместо сжатых**: ×3–4 места при
  копеечном выигрыше (чтение 131 КБ из IDB стоит сравнимо).
