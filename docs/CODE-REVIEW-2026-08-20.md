# Код-ревью 2026-08-20

Ревью ядра приложения (`src/`): ray-marching, DEM-источники, воркер, рендер
панорамы, AR, офлайн-хранилище, Service Worker, навигация. Базовая линия
перед ревью: **`npx tsc` — чисто, `npm test` — 499/499 зелёные** (43 файла).

Вывод: код заметно выше среднего — редкие баги «найди и почини», в основном
точечные нестыковки логики и резервы производительности. Найдено два
заметных бага (офлайн-дыры в скачанных регионах; гонка таймера `setStatus`)
и один реальный резерв скорости, который ничего не ломает (лишний
structuredClone фронтов в воркере).

## 1. Баги (по убыванию важности)

### BUG-1. Офлайн: скачанные тайлы базовой пирамиды недостижимы там, где у hi-слоя лакуны

`src/core/dem-source.ts`, `prefetchAlongRay()`:

```ts
const fineAtOrigin = this.covering(origin, false).length > 0;
for (const p of this.patches) {
  if (p.coarse && fineAtOrigin) continue;   // ← грубая пирамида не тянется вовсе
  ...
}
```

Логика предзагрузки отталкивается от «раз точка наблюдателя покрыта детальным
слоем (hi, 87 м), значит, лучи прочитают hi». Это верно только там, где у hi
**есть тайлы**. Но hi разрежен: у него бывают лакуны («берег, дыра в данных»),
и именно ради этих лакун `keepBaseTileKey()` в `ui/download.ts` сохраняет при
скачивании базовые тайлы 217 м.

В рантайме офлайн получается дыра:
- в ближней зоне (<30 км) порядок опроса `[...fine, terrarium, ...coarse]` —
  Terrarium офлайн пуст, coarse **не предзагружен** → NaN;
- в дальней зоне `[...fine, ...coarse, terrarium]` — то же самое: coarse пуст,
  Terrarium офлайн пуст → NaN.

То есть данные, которые пользователь специально скачал (базовые тайлы лакун),
при расчёте панорамы не используются. Воспроизводится на любом скачанном
регионе p1–p3, у hi которого есть хотя бы одна дырка покрытия, при работе
без сети.

**Фикс (без роста трафика в полностью покрытых местах):** при `fineAtOrigin`
пропускать не весь coarse, а только ячейки, где у fine есть покрытие —
предзагрузка coarse по точкам луча, где `!fine.hasTile(...)` (проверка по
битсету coverage, без сетевых запросов). Либо безусловно предзагружать coarse
в ближней зоне (3×3 вокруг наблюдателя).

### BUG-2. `setStatus`: устаревший таймер стирает более новое сообщение

`src/main.ts`, `setStatus()`:

```ts
if (timeoutMs) {
  setTimeout(() => setStatus(""), timeoutMs);   // хендл не хранится
}
```

Каждый вызов с таймаутом ставит «чистильщика», который через N мс вызывает
`setStatus("")` **без проверки, что на экране уже другое, более новое
сообщение**. Сценарий: «Снимок сохранён» (3 с) → через секунду пользователь
шагнул навипадом → «Расчёт панорамы…» → ещё через 2 с сообщение стирается
посреди расчёта. Та же гонка у всех пар «тост с таймаутом + последующий
статус» (`gpsFailed` 4 с, `calibrateDone` 3 с, `downloadUpToDate` 2.5 с).

**Фикс:** хранить хендл таймера, сбрасывать его при каждом новом вызове
(и не стирать текст, если `setStatus("")` вызван «чужим» таймером — проще
всего `clearTimeout` при входе).

### BUG-3. `annotateIsolation`: вершины без `ele` портят изоляцию друг другу

`src/core/peaks.ts`. Сортировка `(peaks[b].ele ?? 0) - (peaks[a].ele ?? 0)`
классов вершин без `ele` в конец списка, но они **вставляются в сетку**
«уже обработанных = более высоких». Поэтому первая обработанная вершина без
высоты становится фиктивным «более высоким соседом» для следующей — изоляция
второй считается до неё. Смешиваются и настоящие `ele: 0` (прибрежные скалы).

**Фикс:** вершины с `ele === undefined` в сетку не вставлять (свою изоляцию
они при этом честно посчитают от реально более высоких):

```ts
peaks[i].isoM = ...;
if (peaks[i].ele !== undefined) { /* вставка в grid */ }
```

### BUG-4. `smoothLayers`: дальние гребни сглаживаются окном ближней зоны

`src/core/horizon.ts`. Для всех слоёв используется одна `distanceToHorizonM` —
минимум дистанции по корзинам (ближайшая видимая точка луча). Дальний гребень
(100 км), у которого на том же луче виден ближний (1 км), сглаживается окном,
посчитанным от 1 км: `halfWin` до 8 лучей вместо 2, и фильтр разрывов
сравнивает ближние дистанции, а не дистанции дальнего слоя. Острые дальние
пики могут смазываться.

**Фикс:** хранить дистанцию горизонта **на слой** (5 дополнительных
Float32Array — копейки) и сглаживать каждый слой своей дистанцией. Точность
не теряется — наоборот, дальние пики становятся острее.

### BUG-5. `FRONT_CAP = 32`: дальние фронты молча отбрасываются

`src/core/horizon.ts`, `computeLayeredHorizon`. После 32 фронтов на луче новые
локальные максимумы (за провалом >2 км) не записываются — `findPeakMarkerPosition`
их не увидит, маркер вершины уедет на запасную позицию. На 200 км луча в
сложном рельефе 32 фронта достижимы.

**Фикс:** поднять кап (64) либо при переполнении заменять «худший» фронт
(самый низкий максимум), а не отбрасывать новые.

## 2. Ускорение без потери точности

### P1. Воркер: убрать `fronts` из сообщения (минус structuredClone)

`src/workers/horizon.worker.ts` шлёт и `fronts` (массив из тысяч объектов
`VisibleFront`), и плоские `frontsFlat` + `frontsOffsets` (трансфером).
Main использует flat, когда он есть — а он есть всегда: воркер и страница
собираются одним бандлом, ветка «старый воркер» недостижима. При этом
structuredClone `fronts` **платится на каждом compute** — это те самые
«заметные миллисекунды», ради которых вводился flat. Убрать поле `fronts`
из `ResultMessage` и из реконструкции в `main.ts` — точность та же, раз в
несколько мс экономится на каждый пересчёт (drag-перемещения).

### P2. `filterVisiblePeaks`: убрать двойной `azimuthRad` и лишнюю тригонометрию для отсечённых пиков

`src/core/horizon.ts`. Сейчас `azimuthRad(origin, peak)` считается для индекса
в `distanceToHorizonM` и повторно — внутри `checkPeakVisibility` (где один раз
считается `distanceM`; сам он не дублируется). Дополнительно азимут считается
даже для пиков, которых `checkPeakVisibility` отбросил бы до всякой
тригонометрии — по радиусу видимости или отсутствию `ele`. На iberia
(49 тыс. вершин) это десятки мс в воркере на каждую вторую фазу расчёта.
Передать предвычисленный `az` в `checkPeakVisibility` (опциональный аргумент),
а пиков вне радиуса не касаться вовсе — поведение побитово то же.

### P3. `TerrariumSampler.sample`: одна проекция Меркатора на выборку

`src/core/terrarium.ts`. `lonLatToTile` и `lonLatToPixel` считают `normalizeLon`
и `log(tan)+sec` **дважды на каждую выборку** (~4.3 млн выборок на панораму).
Слить в одну функцию, возвращающую и тайл, и дробный пиксель; вынести
`2 ** zoom`, границы широт. По замерам аудита `pointAt` (asin/atan2 +
2×normalizeLon) = 103 мс на панораму — объединение снимает заметную долю.

### P4. Секторные верхние границы для обрыва лучей (задел уже есть)

`loadedMaxHeight` (и `tileMax`) в DemSampler/TerrariumSampler помечены как
«задел для обрыва луча», но в `computeLayeredHorizon` не используются.
Примечание: комментарий у `loadedMaxHeight` в `dem-source.ts` написан в
настоящем времени («Используется обрывом луча (№4)») — он обогнал реализацию,
при внедрении его нужно синхронизировать.
Глобальная граница у горного наблюдателя бесполезна (H > hO), а вот
**секторная с окаймлением** — рабочая: разбить кольцо на 24 сектора, для
каждого хранить max высоты по загруженным тайлам сектора + один тайл
окаймления (консервативно); в марше, если `(sectorMax − drop[s] − hO)/d[s]`
меньше текущего максимума слоя — все оставшиеся шаги сектора пропустить.
Это истинная верхняя граница → точность не меняется, а дальняя треть шагов
(самая дорогая: 350–700 м/шаг) выпадает.

### P5. `switchRegion`: параллелить пики и DEM

`src/main.ts`, `switchRegion()`. Сейчас последовательно:
`fetch(peaks)` (до 8 с на мёртвой сети) → `initDemForRegion` (пробы 2.5 с).
В `main()` они уже параллельны, а при смене региона — нет. `Promise.all`
сокращает худший случай с ~10.5 с до ~8 с без изменений логики.

### P6. Карта: использовать кеш изоляции вместо пересчёта на главном потоке

`src/main.ts`, `setupMapButton()`: для каждого скачанного региона вызывается
`annotateIsolation(peaks)` **на главном потоке**, хотя `main()/switchRegion`
уже сохранили изоляцию в IndexedDB (`saveIsolation`). Для iberia это
~90–400 мс джанка при открытии карты. Фикс: `getIsolation` + `restoreIsolation`,
при промахе — считать порциями в idle (requestIdleCallback) или перекинуть
в воркер.

### P7. Кеш `findPeakMarkerPosition` на версию панорамы

`src/ui/panorama.ts`. Маркер пика (азимут/возвышение фронта) зависит только
от версии панорамы (horizon/layers/fronts), а раскладка подписей
пересчитывается каждый не-stable кадр и заново сканирует окно фронтов для
каждого пика. Кеш `peak → {az, elev}` с ключом-ссылкой на `state.horizon`
(как у `silhouetteCache`) убирает главную стоимость фазы labels.

### P8. Мелочи

- `buildMarchTable`: `if (d[i] >= LAYER_BOUNDS[LAYER_COUNT])` внутри цикла
  по `k` — условие от `k` не зависит, вынести.
- `main.ts`, keydown «назад»: `destination(...)` считается и выбрасывается
  (перетирается `backPos`) — считать только нужную ветку.
- `dem.ts` `loadTile` / `terrarium.ts` `loadTile`: ключ строкой `z/x/y`
  собирается на каждый вызов `tileAt` в горячем цикле — уже закрыт
  last-tile кешем, но можно перейти на числовой ключ `(z << 16) ^ (x << 10) ^ y`
  в Map для полного устранения строк.
- `sampleLod`/`cell`: `this.index!` на каждую ячейку — вынести в локальную
  переменную в начале функции.

## 3. Рекомендуемые регрессионные тесты

- `setStatus`: новое сообщение переживает старый таймаут (BUG-2).
- DemSource: fine-источник с лакуной + coarse-источник → офлайн-выборка
  дальнего шага возвращает высоту из coarse (BUG-1).
- `annotateIsolation`: две вершины без `ele` — изоляция второй не считается
  до первой (BUG-3).
- `smoothLayers` per-layer дистанции: дальний пик на луче с ближним гребнем
  не смазывается (BUG-4).
- `filterVisiblePeaks` с предвычисленным az/dist даёт те же результаты, что
  текущий (P2).
- Воркер без `fronts`: main собирает фронты только из flat (P1).

## 4. Что сделано хорошо (закрепляем)

- Трансфер буферов воркера и latest-only очередь заданий; защита от гонки
  `init`/`compute` через `initPromise` и локальную `source`-ссылку.
- Защита каждого источника DEM от отказов: null-дыры не запоминаются,
  `pending` чистится в `finally`, отклонённые промисы не залипают.
- Офлайн-инварианты продуманы: версионирование пирамиды (`indexVersion`),
  различие 404/503, `Content-Type`-проверка против SPA-fallback.
- Рендер: RDP-децимация с гарантией ≤ 0.5 px, кеш сцены с blit,
  двухслойный AR-оверлей с порогами перерендера, rVFC для видео.
- Геометрия: защита антимеридиана повсюду (Врангель), побитовое совпадение
  `makeRayMarcher` с `destination`, защёлка детектора системы координат датчика.
- Комментарии уровня «почему так, а не иначе» почти у каждой неочевидной
  строки — это удерживает всю команду (и будущего себя) от регрессий.
