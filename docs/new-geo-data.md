Короткий ответ: \*\*не изобретайте своё хранилище DEM — берите готовый глобальный слой AWS Terrain Tiles (Terrarium PNG) как базовый источник для всего мира, а поверх — свои LOD-патчи для горных регионов\*\*. Это единственный вариант, где «весь мир» не превращается в терабайты и годы поддержки.



\## Архитектура источника геоданных (3 слоя)



```

Слой 1. Глобальный базовый DEM — ЧУЖОЙ, готовый, бесплатный

&#x20;  AWS Open Data «Terrain Tiles» (Mapzen Joerd): s3://elevation-tiles-prod

&#x20;  • Покрытие: весь мир, 85°S–85°N

&#x20;  • Источники уже склеены: SRTM + ETOPO1 + GMTED + NED/3DEP + ArcticDEM + GLO-90…

&#x20;    → проблема «SRTM не покрывает >60°N» решена сама, ледники/Антарктида включены

&#x20;  • Формат: Terrarium PNG, зумы 0–15 (\~90 м на экваторе на z15)

&#x20;  • Декодирование в JS — 1 строка:

&#x20;    h = (R·256 + G + B/256) − 32768

&#x20;  • Лицензия: открытая (PDDL/разрешение Mapzen), CDN-класс S3



Слой 2. Горные LOD-патчи — СВОИ (там, где нужно качество)

&#x20;  • Регионы интереса (Кавказ, Алтай, Альпы, Гималаи…) → наши int16-тайлы

&#x20;    из SRTM V3 void-filled / GLO-90 / AW3D30 по DATA-PIPELINE.md

&#x20;  • 90 м в радиусе 30 км, 250–500 м до 200 км; brotli; \~5–15 МБ на регион

&#x20;  • Хостинг: GitHub Pages (тариф 1 ГБ мягкий — десятки регионов влезают)



Слой 3. Вершины — СВОИ, прекомпилированные

&#x20;  • Регионы: peaks/{region}.json из Overpass (как раньше)

&#x20;  • Весь мир: один global-peaks.json по Wikidata SPARQL

&#x20;    (instance of mountain + ele + coords; \~50–100 тыс. записей, 3–6 МБ gzip)

&#x20;  • Обновление: GitHub Action ежемесячно → PR с диффом

```



\## Как это работает в приложении



```

Запрос тайла(регион, lod, x, y):

&#x20;   если есть локальный патч (IndexedDB)        → наш int16 (офлайн, точный)

&#x20;   иначе если онлайн                           → AWS Terrarium PNG (весь мир)

&#x20;   иначе                                       → деградация: грубый зум Terrarium

&#x20;                                                 из кеша / честное «нет данных»

```



Воркеру без разницы: оба декодируются в `Float32Array`/`Int16Array` высот. Единая функция `sampleDEM(lat, lon)` прячет источник — ray-marching не меняется вообще.



\## Почему это «удобно», а не компромисс



| Критерий | Оценка |

|---|---|

| Весь мир из коробки | ✅ z0–15, включая Камчатку, Хибины, Антарктиду — без единой строчки ETL |

| Холодный старт MVP | ✅ день 1: ray-marching читает Terrarium напрямую — пайплайн тайлов можно отложить на неделю 2 |

| Офлайн в горах | ✅ решается слоем 2 (патчи); глобальный слой офлайн не нужен — в глуши всё равно нужен заранее скачанный регион |

| Объём нашего хостинга | ✅ только горные патчи (\~10 МБ × N регионов), а не планета |

| Точность там, где важно | ✅ патчи дают void-filled 90 м; Terrarium в горах РФ — та же SRTM внутри, так что расхождение минимально |

| Лицензии | ✅ Terrarium PDDL-подобная; наши патчи — public domain / CC-BY (GLO-90, атрибуция в «О приложении») |



\## Подводные камни (честно)



1\. \*\*Зависимость от чужого бакета.\*\* `elevation-tiles-prod` живёт на AWS Open Data с 2017 года и используется кучей проектов, но гарантий нет. Митигация: слой 2 всё равно свой; позже можно зеркалировать нужные зумы.

2\. \*\*z15 = 90 м только на экваторе.\*\* На широте 65° (Хибины) ячейка \~90 м·cos(65°)≈38 м по X — норм; но максимальный зум ограничен z15 → для «крутых» регионов патч 30 м (AW3D30) всё же лучше.

3\. \*\*Terrarium PNG вместо int16\*\* — +декодирование (тривиально) и нельзя brotli-сжать PNG на статике с пользой. Не проблема: это онлайн-слой.

4\. \*\*Территориальные споры в данных Wikidata\*\* (названия/границы) — для РФ-аудитории фильтровать name:ru из OSM-регионов приоритетнее Wikidata.
