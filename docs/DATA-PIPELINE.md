# Пайплайн данных

## Архитектура геоданных (3 слоя)

```
Слой 1. Глобальный базовый DEM — ЧУЖОЙ, готовый, бесплатный
  AWS Open Data «Terrain Tiles» (Mapzen Joerd): s3://elevation-tiles-prod
  https://s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png
  • Покрытие: весь мир, 85°S–85°N (SRTM + ETOPO1 + GMTED + NED + ArcticDEM + GLO-90)
    → проблема «SRTM не покрывает >60°N» решена для онлайн-режима
  • Формат: Terrarium PNG, зумы 0–15; CORS: Access-Control-Allow-Origin: *
  • Декодирование: h = R·256 + G + B/256 − 32768
  • Пиксель z15 ≈ 4.8 м на экваторе, но данные внутри — класса 90 м (SRTM 3″);
    зум выбирается по дальности луча: <30 км → z15, <100 км → z13, <200 км → z11
  • Проверено: тайл Эльбруса даёт 5631.8 м (реальность 5642 м)

Слой 2. Горные LOD-патчи — СВОИ (там, где нужно качество и офлайн)
  Глобальная пирамида из GLO-90 (раздел «Глобальная пирамида» ниже) —
  tiles/global, ~947 МБ на всю планету (217/435 м / 1.7 км), офлайн везде.
  Детальный слой ~87 м для регионов приоритета 1–3 плюс верхушки p4 —
  tiles/hi в agran/vershiny-dem-hi (~957 МБ), см. «Детальный слой ~87 м».
  Плюс, при необходимости, детальные 90-м патчи отдельных регионов
  (tools/dem-to-tiles) — они приоритетнее обеих пирамид.

Слой 3. Вершины — СВОИ, прекомпилированные
  Регионы: peaks/{region}.json из Overpass; весь мир (позже): global-peaks.json
  по Wikidata SPARQL; name:ru из OSM приоритетнее Wikidata для РФ-аудитории.

Запрос тайла в приложении (src/core/dem-source.ts):
  детальный патч региона (90 м)      → он и есть истина
  hi-пирамида tiles/hi (87 м, p1–p3) → детальный офлайн, приоритетнее сети
  онлайн Terrarium PNG (весь мир)    → в ближней зоне точнее базовой пирамиды
  базовая пирамида tiles/global      → офлайн и вся дальняя зона
  иначе                              → деградация: кеш / честное «нет данных»
```

## DEM (рельеф) — горные патчи

### Источники (по широте!)
| Источник | Покрытие | Разрешение | Лицензия |
|---|---|---|---|
| SRTM V3 **void-filled** | до 60°N | ~90 м (3″) | Public domain (NASA) |
| Copernicus GLO-90 | глобально | 90 м | свободная, с атрибуцией © DLR/ESA |
| ALOS AW3D30 | глобально | 30 м | JAXA, открытая с регистрацией |

⚠️ **SRTM севернее 60°N отсутствует** — Хибины, Полярный Урал, Путорана → GLO-90/AW3D30.
  (Для онлайн-режима это закрывает слой 1; GLO-90 нужен только для офлайн-патчей.)
⚠️ **Только void-filled версии** — в сырых SRTM дыры на крутых склонах и ледниках (ровно там, где нужно).

### Формат тайлов
- Тайл 256×256, значения int16 little-endian (высоты в метрах), без заголовка
- Индекс `index.json`: bbox, размер ячейки в градусах, список LOD
- **LOD-схема** (дальним хребтам не нужна детализация — их угловой размер мал):
  - радиус 0–30 км от центра региона: 90 м
  - 30–200 км: 250–500 м (даунсэмпл средним, не ближайшим — иначе теряются гребни)
- Сжатие: brotli статикой на GitHub Pages; ожидаемый объём региона 400×400 км ≈ **5–15 МБ**

### Пайплайн
```
download (Earthdata/AWS Open Data / JAXA)
  → gdal_merge / gdalwarp в EPSG:4326
  → dem-to-tiles: нарезка + даунсэмпл LOD + int16
  → tools/validate: сравнение высот известных вершин с OSM ele (расход >50 м = флаг)
  → выкладка в /tiles/{region}/
```

## Глобальная пирамида GLO-90 (tools/glo90-to-tiles)

Регионы в `regions.json` сильно перекрываются, а нарезать каждый по-отдельности
в 90 м — это ~67 ГБ. Поэтому весь мир лежит одной **разреженной пирамидой**,
а регион — просто bbox поверх неё.

Данные (~947 МБ) не помещаются в репозиторий приложения, поэтому живут отдельно:
**[agran/vershiny-dem](https://github.com/agran/vershiny-dem)** → GitHub Pages.
Адрес и порядок фолбэка задаются в `src/core/dem-config.ts`.

```
https://agran.github.io/vershiny-dem/tiles/global/{lod}/{x}/{y}.bin.gz
https://agran.github.io/vershiny-dem/tiles/global/index.json
```

Уровень задаётся числом ячеек в градусе N; тайл 256 ячеек = 256/N градусов,
поэтому границы тайлов ложатся на градусную сетку исходников GLO-90:

| LOD | N | Ячейка | Тайл | Что покрывает |
|---|---|---|---|---|
| 0 | 512 | ~217 м | 0.5° | горы (размах ≥300 м), квант 4 м, доля бюджета 0.60 |
| 1 | 256 | ~435 м | 1° | рельефная суша (≥150 м), квант 4 м, доля 0.30 |
| 2 | 64 | ~1.7 км | 4° | вся суша, без лимита (~104 МБ) |

Фактический прогон (2026-08-18, бюджет 1050 МБ): 947 МБ. LOD 0 обрезан
бюджетом (28% ячеек-кандидатов): хвост — плоские ячейки p4 (Антарктида −2069,
Бразилия, Гренландия, Аляска) и «ничейная» земля вне реестра (рельеф на
границе ~1200 м); p1–p3 покрыты целиком. LOD 1 обрезан на 25%, но все
пропущенные — вне регионов (рельеф <775 м).

Сетка глобальная и общая для всех уровней: ячейка `i` — точка
`lon = −180 + i/N`, `lat = 90 − j/N` (пиксель-точка, как и в исходном COG).

**Формат тайла**: значения `h/quantM` → дельта вдоль строк → gzip. Клиент
распаковывает `DecompressionStream('gzip')` (на старых браузерах — `fflate`),
накапливает дельту с
переполнением int16 и умножает на `quantM`. GitHub Pages бинарники не жмёт,
поэтому сжатие своё: ~2× к объёму и трафику. Альтернативы измерены на
реальных тайлах (`tools/codec-bench/codec_bench.py`, см. STATUS.md «Запас до
лимита Pages»): PNG-2×8bit проигрывает gzip, Paeth+Rice дал бы −15%, но
требует своего TS-декодера — отложено.

**Разреженность**: тайла может не быть (море, равнина, не влез в бюджет).
`index.json` содержит base64-битсет `coverage` на каждый LOD — клиент не тратит
запрос на заведомо отсутствующий тайл, а `DemSampler.sample()` при дыре на
детальном уровне сам уходит на более грубый, затем на Terrarium. Там же лежит
`avgTileBytes` на LOD: по нему панель настроек честно считает вес офлайн-загрузки
региона (тайлы в bbox × средний вес), не гадая по площади.

Известное ограничение: интерполяция не сшивает антимеридиан (±180°) — луч,
пересекающий его, там получает NaN и уходит на Terrarium. Затрагивает только
Чукотку/Алеуты; проще жить с этим, чем дублировать столбец на каждом уровне.

**Отбор по бюджету**: ячейки 1° сортируются по приоритету региона из
`regions.json` (сначала все p1, затем p2…), внутри группы — по размаху высот;
уровень наполняется сверху вниз, пока не исчерпан его бюджет. Сортировка по
одному лишь размаху отдала бы весь детальный уровень Гималаям и Андам, а
Хибины с Уралом (приоритет 1–2, размах ~1 км) остались бы вообще без него.
По той же причине порог рельефа для приоритетных регионов смягчается
(`PRIORITY_WEIGHT`). Итоговый размер известен точно, а не по оценке.

### Исходники: скачивание GLO-90

**Copernicus DEM GLO-90** — AWS Open Data, без регистрации: бакет
`s3://copernicus-dem-90m/` (eu-central-1), Cloud-Optimized GeoTIFF 1°×1°,
лицензия свободная с атрибуцией © DLR/ESA.

```powershell
winget install Amazon.AWSCLI

# Вся планета: 26 475 папок, ~175 ГБ вместе с AUXFILES (около суток на бытовом канале).
# aws s3 sync идемпотентен: после обрыва просто повторите ту же команду.
aws s3 sync s3://copernicus-dem-90m/ ./dem/glo-90/ --no-sign-request

# Только DEM без вспомогательных слоёв — примерно вдвое меньше
aws s3 sync s3://copernicus-dem-90m/ ./dem/glo-90/ --no-sign-request `
  --exclude "*/AUXFILES/*" --exclude "*/PREVIEW/*" --exclude "*/INFO/*"
```

Имена в бакете — `COG_30` (не `90`) с суффиксом `_DEM`; `30` здесь — угловые
секунды, это и есть ~90 м на экваторе. `N43_00_E042_00` — юго-западный угол
клетки: `Copernicus_DSM_COG_30_N43_00_E042_00_DEM/…_DEM.tif`. Папка `dem/`
в `.gitignore`.

### Сборка пирамиды

```powershell
# статистика исходников (кеш dem/glo-90-scan.json, ~5 мин на 26 475 тайлов)
python tools\glo90-to-tiles\glo90_to_tiles.py scan

# план: сколько тайлов и МБ влезет (замеряет настоящие тайлы, ничего не пишет)
python tools\glo90-to-tiles\glo90_to_tiles.py build --dry-run

# обе репозитории одной командой (scan → base → hi):
python tools\dem-pipeline.py --skip-scan

# только базовая пирамида: бюджет 1050 МБ, доли LOD 0.60/0.30/без лимита
python tools\glo90-to-tiles\glo90_to_tiles.py build --budget-mb 1050 `
  --levels "512:2:400:0.60,256:4:150:0.30,64:8:0:-" `
  -o ..\vershiny-dem\tiles\global --clean

# один район детальнее (например, перегенерировать Приэльбрусье)
python tools\glo90-to-tiles\glo90_to_tiles.py build --only-region elbrus --budget-mb 40
```

Ключи: `--workers N` (по умолчанию ядра−1), `--only-region elbrus`,
`--only-priority 1,2,3` (фильтр по приоритетам регионов — для детального
слоя), `--clean` (пересобрать с нуля — нужно, если менялись уровни или
правила отбора), `--levels N:квант:мин_размах:доля_бюджета` (своя лестница
уровней).

Локальная копия в `public/tiles/global` тоже работает (клиент проверяет её
раньше внешнего адреса), но в `public/` держать её не стоит: 26 тыс. файлов
замедляют старт Vite с 0.25 до 4.6 с.

Проверено на Приэльбрусье: Приют 11 → 4134 м (реально ~4050 м, ячейка 217 м
на склоне, квант 4 м), Азау → 2330 м (реально ~2350 м), вершина Эльбруса →
5524 м (5642 м; пик сглажен размером ячейки — это ожидаемо).

| Этап | Время |
|---|---|
| Скачивание планеты (~175 ГБ) | около суток на бытовом канале |
| `scan` (26 475 тайлов) | ~5 мин, кешируется |
| `build --dry-run` | ~1–2 мин |
| `build` планеты в 900 МБ | ~4 мин (16 воркеров) |
| `build --only-region` | секунды-минуты |

### Детальный слой ~87 м (agran/vershiny-dem-hi)

Лимит Pages (1 ГБ/сайт) не дал вложить родные 90 м в базовую пирамиду — она
ужата до 217/435 м в 947 МБ. Детальный слой живёт во втором репозитории
[agran/vershiny-dem-hi](https://github.com/agran/vershiny-dem-hi) со своим
Pages, `tiles/hi/{lod}/{x}/{y}.bin.gz`:

| LOD | N | Ячейка | Тайл | Что покрывает |
|---|---|---|---|---|
| 0 | 1280 | ~87 м | 0.2° | p1–p3 целиком (1130 ячеек 1°) + верхушки p4 по остатку бюджета; квант 2 м, порог размаха 100 м |

Итого 28 250+ файлов, ~957 МБ. Грубого LOD 1 в hi нет: клиент в дыре уходит
на базовую пирамиду, где тот же уровень уже есть (дубль был мёртвым грузом).
Клиент подключает слой
одним из кандидатов (`GLOBAL_DEM_HI_URL` в `dem-config.ts`) наряду с базовой
пирамидой: `DemSource` держит цепочку источников и классифицирует каждый по
`finestResM() ≤ 120 м` — hi-слой «свой» и приоритетнее Terrarium всегда,
базовая пирамида (217 м) — офлайн-запас вдали. Разреженность hi покрывается
фолбэком: вне p1–p3 работает базовая пирамида.

```powershell
# детальный слой: p1–p3 + самые горные p4, бюджет 950 МБ (~2 мин на 16 воркерах)
# ⚠️ доля уровня «1.0» обязательна: «-» = inf, и --budget-mb не действует
# вообще (первый прогон так ушёл за 1 ГБ)
python tools\glo90-to-tiles\glo90_to_tiles.py build --only-priority 1,2,3,4 `
  --levels "1280:2:100:1.0" --budget-mb 950 -o ..\vershiny-dem-hi\tiles\hi --clean
```

Контрольные высоты совпали с исходным GLO-90: Эльбрус 5528 м (максимум ячейки
тайла 5615 м — ближе к 5642 м, чем 5590 м базовой пирамиды), Приют 11 — 4133 м.

### Детальный патч отдельного региона (90 м)

Патч приоритетнее пирамиды — если району нужна максимальная детализация:

```powershell
# Слияние тайлов в один GeoTIFF (COG лежат по подпапкам)
gdal_merge.py -o dem/elbrus-merged.tif (Get-ChildItem dem/elbrus -Recurse -Filter *_DEM.tif).FullName

# Перепроекция в EPSG:4326 (уже в нём, но на всякий случай)
gdalwarp -t_srs EPSG:4326 -tr 0.000833333 0.000833333 dem/elbrus-merged.tif dem/elbrus-90m.tif

python tools/dem-to-tiles/dem_to_tiles.py dem/elbrus-90m.tif -o public/tiles/elbrus
```

Патч подхватывается автоматически: `DemSource` сначала спрашивает его, затем
hi-слой (p1–p3, ~87 м), затем базовую пирамиду, затем Terrarium.

Ссылки: [реестр AWS](https://registry.opendata.aws/copernicus-dem/),
[документация бакета](https://copernicus-dem-90m.s3.amazonaws.com/readme.html).

## Вершины (POI)

- Источник 1: **Overpass API** (онлайн, требует доступ):
  `node["natural"="peak"](bbox);` **и** `node["natural"="volcano"](bbox);`
- Источник 2: **planet.osm.pbf + tools/planet-peaks** (офлайн, полный контроль):
  `planet_peaks.py planet.osm.pbf --bbox 42.0,41.8,45.0,44.9 -o peaks.jsonl`
  затем `peaks_to_json.py --from-file peaks.jsonl`
- **Индекс поиска**: `tools/peaks-index/build_index.py` собирает
  `public/peaks/_index.json` — по 400 значимых вершин каждого региона
  (43 462 записи, 2.4 МБ). Нужен, чтобы поиск находил вершины регионов,
  которые пользователь не открывал. Пересобирать после регенерации peaks/*
  (входит в `tools/peaks-pipeline.py`).
  Отбор учитывает `wikidata`/`wikipedia` как признак известности —
  без него выпадали хоженые вершины вроде Оштена (ALGORITHMS.md §6).
- ⚠️ **Вулканы в OSM — это `natural=volcano`, а не `peak`.** Забыть про них
  значит потерять Эльбрус, Казбек, Фудзи, Килиманджаро, Демавенд, Ключевскую
  и целые регионы реестра (Камчатка, Эквадор, Центральная Америка). Ровно это
  и случилось в первой версии: Эльбруса не было в `peaks/elbrus.json`.
  Вулканы помечаются полем `volcano: true`.
- Поля: `name:ru` → fallback `name` → `name:en`, `ele`, `lat/lon`, `wikidata`
- **`prominence` в OSM почти не заполнен** — вместо него считаем **изоляцию**
  (расстояние до ближайшей более высокой вершины) прямо в приложении из
  загруженного набора: `annotateIsolation` в `src/core/peaks.ts`, подробности
  в ALGORITHMS.md §5. Приоритет подписи:
  `ele · (1 + 0.4·exp(−d/40км)) · w(изоляция)`, при наложении на экране
  показываем топ-N, остальные в кластер «+3»
- Выход: `peaks/{region}.json`, ~200–500 КБ gzip на Кавказ
- Обновление: ежемесячный GitHub Action → PR с диффом (видно вандализм в OSM)
- Пользовательские правки из приложения (v1.1) идут **в OSM**, не в нашу базу

## Реестр регионов (tools/regions.json)

Регион = «местность одного похода» + буфер ≥200 км (макс. дальность видимости,
ALGORITHMS.md). Границы — по горным системам, названия — как у туристов.
Перекрытия соседних регионов — норма: дубли пиков весят копейки, зато нет
«слепых зон» на стыках. Один регион = одна кнопка «Скачать» в приложении,
целевой размер ≤20 МБ (ROADMAP, критерии приёмки).

Полный список (**124 региона**) — в `tools/regions.json`. Покрытие: весь мир,
включая Килиманджаро (east-africa + свой kilimanjaro), Крым, Фудзи,
Монблан, Тубкаль, Патагонию (patagonia + patagonia-south), Антарктиду,
Гренландию, Шпицберген. Ключевые группы:

## Хранение на устройстве

IndexedDB (`src/core/db.ts`, версия 4) — тайлы лежат **как есть, сжатыми**:
распаковка одного тайла занимает доли миллисекунды, а место экономит вчетверо.

| Стор | Ключ | Содержимое |
|---|---|---|
| `dem-tiles` | `lod/x/y` | gzip-байты тайла пирамиды (~34 КБ) |
| `terrarium` | `z/x/y` | PNG Terrarium как скачан (~60 КБ) |
| `peaks` | регион | вершины региона |
| `meta` | `region:*`, `dem-index:*`, `regions` | отметки о загрузке, кеш `index.json`, реестр регионов |

Кеш `index.json` обязателен: без него офлайн не стартует даже то, что уже лежит
в хранилище. По той же причине кешируется и реестр регионов: без него офлайн
список регионов пуст и активный регион не сменить — даже на скачанный.

- Service Worker: cache-first для тайлов, network-first для данных
  (`index.json`, `peaks/*`, `regions.json`) — второй, независимый слой офлайна
  (переживает очистку IndexedDB и наоборот). Чанки приложения кладутся в кеш
  при установке worker'а: иначе офлайн открывалось только то, что человек
  успел открыть при сети. Кеши тайлов и данных не привязаны к версии
  оболочки — иначе каждое обновление приложения отбирало бы офлайн-запас
- «Скачать регион»: пирамида по bbox + Terrarium в круге 30 км вокруг точки,
  медиана 13 МБ (см. STATUS.md → «Офлайн-загрузка региона»)
