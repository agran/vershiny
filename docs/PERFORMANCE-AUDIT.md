# Аудит производительности PWA «Вершины»

> Дата: 2026-08-18  
> Версия: по коммиту 876f9ab и последующим правкам (TILE_CACHE v2)  
> Цель: панорама < 500 мс, кадр < 16 мс на слабом смартфоне (4–6 лет)

## Контекст и методология

Код изучен вручную:
`src/core/{horizon,dem,dem-source,geo,terrarium,peaks,skyline-match}.ts`,
`src/workers/horizon.worker.ts`, `src/ui/{panorama,ar}.ts`, `src/sw.ts`.

Подтверждено, что реальная панорама для Приэльбрусья использует **1 600 пиков**
в файле `public/peaks/elbrus.json`.

Уже оптимизировано (876f9ab, **не предлагается повторно**): ядро ray-marching
(таблица марша, makeRayMarcher, сравнение наклонов, кеш последнего тайла/источника,
SoA-накопление фронтов, досрочный обрыв луча пика, tileMax при декодировании).
Итог бенчмарка ядра: 250 → 171 мс на десктопе.

### 1. tileMax посчитан, но ранний обрыв луча по нему не реализован → ~540 шагов вместо возможных 100–200

**Файлы:** `src/core/horizon.ts` → `computeLayeredHorizon`;
`src/core/dem.ts` → `decodeTile` + `tileMax`

**Что происходит.**  
В `decodeTile` (dem.ts строка 582) при каждом декодировании тайла сохраняется
максимальная высота пикселя во всём тайле 256×256:

```ts
this.tileMax.set(`${lodIndex}/${keyTail}`, max * quant);
```

Это значение **нигде не используется** в горячем цикле ray-marching.

Текущий ранний выход (horizon.ts строки 389–392):

```ts
if (d > 60_000 && slope < binExitSlope[bin] && binMaxAngle[bin] < -0.005)
    break;
```

Условие `binMaxAngle[bin] < -0.005` («горизонт ниже −0.3°») для **горного
наблюдателя** (Приют-11, 4 130 м) почти никогда не выполняется на лучах в
сторону вершин: горизонт там положительный или около нуля. Из 3 600 лучей
прерываются досрочно только те, что смотрят в долину; лучи в сторону Эльбруса,
Ушбы, Казбека проходят **все ~540 шагов**.

**Фикс.** Перед входом в блок шагов, принадлежащих тайлу, проверять
`tileMax["lod/tx/ty"]`. Если даже эта верхняя граница не даёт нового максимума
угла — весь тайл пропускается. Тайл LOD 0 (90 м) охватывает ~23 км дальности
≈ 128 шагов при шаге 180 м — ровно столько экономится на тайл.

Реализация: добавить метод `tileUpperBound(pos, distM, hint): number` в
`DemSource`, блочный цикл в `computeLayeredHorizon`.

**Корректность.** `tileMax` — строгая верхняя граница. Если она не бьёт текущий
максимум, ни один реальный пиксель тайла его не побьёт. Результат **побитово
идентичен**. Тест: сравнить `Float32Array` горизонта до/после по 1 000 случайных
точек.

**Ожидаемый эффект.** −20–40% шагов в дальней зоне (60–200 км), где
сосредоточены ~2/3 итераций. На телефоне: **−75–120 мс** при горячем кеше.

**Риск / сложность:** низкий / средняя (нужно пробросить `tileMax` через
DemSource → SampleFn или отдельный метод).

### 2. filterVisiblePeaks: 1 600 пиков × (haversine + atan2 + ray-march до пика)

**Файл:** `src/core/horizon.ts` — `filterVisiblePeaks` (стр. 567),
`checkPeakVisibility` (стр. 480)

**Что происходит.** Для каждого из 1 600 пиков вызывается
`checkPeakVisibility`, в которой:

1. `distanceM` — haversine: sin×2, cos×1, asin×1, sqrt×1 = 5 триг-операций
2. `azimuthRad` — atan2 + 4×trig = 5 операций (вызывается **дважды**:
   строка 574–579 для индексации `distanceToHorizonM` и внутри
   `checkPeakVisibility`)
3. `makeRayMarcher` — ещё 4 триг + closure-аллокация
4. Внутренний цикл марша до `dist − 100` м: для пика в 100 км ≈ 555 итераций

Тrig-операции: 1 600 × 14 = **22 400 вызовов** sin/cos/asin/atan2 на
расстояния/азимуты. На ARM Cortex-A55 (~75 нс/вызов) → ≈ **1.7 мс** только тригонометрия. Полный марш 1 600 лучей до пиков: ~300 000 итераций → **15–30 мс на телефоне**.

**Фикс А.** Предвычислять `distanceM` + `azimuthRad` один раз и передавать в
`checkPeakVisibility`, убрав дублирование (сейчас `azimuthRad` считается дважды).

**Фикс Б (основной).** Батч-предфильтрация без марша: если
`peak.ele − hO − earthDrop(dist) < (horizon[azIdx] − 2°) × dist`, пик явно
скрыт — вернуть `hidden` без полного ray-march для ~80% пиков в горном регионе.
Пороговые пики (в пределах 2°) всё равно проверяются полным маршем.

**Корректность.** Пики, скрытые глубже 2°, не получают маркер независимо от
точного угла. Разница только в `hiddenDeficitM` — не влияет на отображение при
таком запасе.

**Ожидаемый эффект.** **−15–25 мс** (телефон).

**Риск / сложность:** низкий / низкая.

### 3. AR-режим: полный redraw на каждый requestAnimationFrame

**Файлы:** `src/ui/ar.ts` (стр. 284–286), `src/ui/panorama.ts` — `drawOverlay`,
`silhouetteProfile`, `buildRidgeSegments`, `drawLabels`, `liftAboveSilhouette`

**Что происходит на каждый кадр (бюджет 16 мс при 60 fps):**

| Операция | Аллокации | Итераций |
|---|---|---|
| `silhouetteProfile` | `new Float32Array(3 600)` каждый кадр | 14 профилей × 3 600 = 50 400 |
| `buildRidgeSegments` × 8 | массивы `{x,y}[]` | 8 × 3 600 = 28 800 |
| `runningMax` | `new Float32Array(3 600).fill(−Inf)` | — |
| `strokeRidge` × 16 (8 профилей × 2 цвета) | — | 16 × `ctx.stroke()` |
| `liftAboveSilhouette` / `clipToSilhouette` | — | до 52 × 5 `horizonAtAzimuth` |

`silhouetteProfile` выделяет 14 400 байт × 60 кадров/с = **840 КБ/с молодых
объектов** → minor GC раз в несколько секунд на Cortex-A55.

**Фикс А.** Кешировать `silhouetteProfile` как часть `PanoramaState`,
вычислять один раз при получении `ResultMessage` от worker'а.

**Фикс Б.** Переиспользовать буфер `runningMax` (выделять один раз, сбрасывать
через `runningMax.fill(−Infinity)`).

**Фикс В.** Объединить 8 + 8 `ctx.stroke()` в 2: один `Path2D` для тёмных
линий всех профилей, один для светлых.

**Фикс Г.** Кешировать `placed[]` из `drawLabels`: подписи не меняются, пока
`view.centerAzRad` не изменился на > 0.5°.

**Корректность.** `silhouetteProfile` детерминирован по `PanoramaState`.
Кеш инвалидируется при новом `ResultMessage`. Рендер **побитово идентичен**.

**Ожидаемый эффект.** Кадр: 15 мс → **10–12 мс**, что укладывается в 16 мс на
Snapdragon 430. Суммарно: **−4–6 мс/кадр**.

**Риск / сложность:** очень низкий / низкая.

### 4. Prefetch-веер: 72 луча × 3 источника = 216 prefetchAlongRay за расчёт

**Файл:** `src/workers/horizon.worker.ts` (стр. 132–136)

```ts
for (let az = 0; az < 2 * Math.PI; az += (5 * Math.PI) / 180) {
    prefetchTasks.push(
      source.prefetchAlongRay(origin, az, MAX_DIST_M, 8_000, destination),
    );
}
```

360° / 5° = **72 луча**. На регионе hi + global это 2 источника → 144
параллельных промиса (216 с Terrarium).

Внутри `TerrariumSampler.prefetchAlongRay` (terrarium.ts стр. 358–379):
72 × 25 точек = **1 800 вызовов `destination()`** + 1 800 итераций `Set`.

Реальная проблема — **перекрытие тайлов**: на z9 тайл охватывает ≈ 78 × 78 км.
Большинство лучей дальней зоны попадают в одни и те же 10–20 тайлов, но каждый
луч строит свой `Set` и выдаёт `loadTile(...)` — который возвращает кеш-хит,
но создаёт объект промиса. Итого: ~5 400 microtask-переключений + GC-мусор.

**Фикс А.** Дедупликация на уровне `DemSource.prefetchAlongRay`: собирать
глобальный `Set` ключей по всем источникам до запуска `loadTile`.

**Фикс Б.** Прореживание по зуму: для z9 (тайл 78 км) шаг `8 000` м избыточен —
достаточно одной точки на тайл (~40 км).

**Ожидаемый эффект.** Сокращение промисов с ~200 до ~30–40 уникальных.
Ускорение prefetch-фазы: **−15–30 мс**.

**Риск / сложность:** низкий / низкая–средняя.

### 5. decodeTile: 65 536 умножений на quant на каждый тайл при холодном кеше

**Файл:** `src/core/dem.ts` — `decodeTile` (стр. 537–583)

После пересборки GLO-90 (2026-08-18) `quantM` LOD 0 = 4 м/ед. При декодировании:

```ts
if (quant !== 1) {
    for (let i = 0; i < values.length; i++) values[i] *= quant;
}
```

65 536 умножений Int16 × 80 тайлов первого расчёта = **5.2 млн операций**
≈ 10 мс на ARM Cortex-A55.

Дополнительно: фильтр delta-x (стр. 560–574) — ещё 65 536 итераций с
принудительным bit-shift для int16-overflow:

```ts
acc = ((acc + values[row + x]) << 16) >> 16;
```

Это затрудняет JIT-оптимизацию в V8/JSC: движок теряет тип-подсказку,
что особенно заметно на Cortex-A55 без SIMD.

**Фикс (лучший).** Вынести `quant` из декодирования в `cell()`:
хранить `Int16Array` без умножения, умножать при чтении:

```ts
return tile[cy * TILE_SIZE + cx] * quant;
```

`cell()` вызывается 4 раза на сэмпл (билинейная интерполяция) вместо
65 536 при декодировании — в **16 384 раза меньше** умножений суммарно.
`tileMax` хранить без quant, умножать при сравнении.

Хранить в IndexedDB `Int16Array` без quant (корректно при смене quant без
инвалидации тайлов).

**Корректность.** `cell() × quant` vs `cell_premultiplied` — арифметически
тождественно (int16 × int = точная целочисленная операция для высот до 32 767 м).

**Ожидаемый эффект.** **−5–15 мс** холодного старта. Нейтрально при горячем кеше.

**Риск / сложность:** очень низкий / низкая.

## Дополнительные наблюдения

**smoothLayers** (horizon.ts): 5 слоёв × 3 600 лучей × окно до 17 = 306 000
операций с хорошей локальностью. Потенциал: in-place сглаживание со скользящей
суммой. Выигрыш ~5–8 мс — ниже порога топ-5.

**skyline-match БПФ** — только при CV-калибровке, не на критическом пути
«открыть панораму». Не рассматривается.

**Service Worker** не блокирует первый расчёт. Динамические импорты в `main.ts`
(analytics, ar, photo, search, calibration) ленивые. По критическому пути
выполняется только `loadRegions` + `getPosition` + отправка `compute` в worker.

## План измерения до/после на реальном телефоне

### Instrumentation в worker

Добавить в `horizon.worker.ts` перед `compute()`:

```ts
performance.mark('compute-start');
// ... после prefetch:
performance.mark('prefetch-done');
// ... после computeLayeredHorizon:
performance.mark('march-done');
// ... после filterVisiblePeaks:
performance.mark('peaks-done');
```

В `ResultMessage` добавить поля `prefetchMs`, `marchMs`, `peaksMs`.
Main.ts пишет их в `localStorage`:

```ts
const perf = JSON.parse(localStorage.getItem('vershiny-perf') ?? '[]');
perf.push({ ts: Date.now(), prefetchMs, marchMs, peaksMs, totalMs });
localStorage.setItem('vershiny-perf', JSON.stringify(perf.slice(-50)));
```

### Измерение AR-кадра

В `drawArFrame` оборачивать `performance.now()`:

```ts
const t0 = performance.now();
drawOverlay(...);
const frameMs = performance.now() - t0;
if (frameMs > 12) console.warn(`AR slow frame: ${frameMs.toFixed(1)} ms`);
```

### Процедура

1. Chrome DevTools Remote на Android 5–7-летней давности (Snapdragon 430/450).
2. Вкладка Performance → записать 10 с со свайпами панорамы.
3. Отметить Long Tasks (> 50 мс) в главном потоке и в Worker.
4. `performance.memory.usedJSHeapSize` до и после расчёта.
5. Сравнить `localStorage['vershiny-perf']` до/после каждого фикса.
