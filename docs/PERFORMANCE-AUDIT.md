# Аудит производительности PWA «Вершины»

> Дата: 2026-08-19. База: коммит 876f9ab + правки до 399c63d (HEAD).
> Тесты на момент аудита: 410/410 зелёные.
> Смежный документ: `docs/PERFORMANCE-AUDIT-FROM-Claude Sonnet 4.6.md`
> (более ранний аудит; расхождения с ним отмечены в §6).
>
> Цели: панорама < 500 мс, кадр < 16 мс на смартфоне 4–6 лет.
> Сейчас: расчёт ~770 мс на десктопе (worker, горячий кеш), ~2 с с холодным;
> на телефоне ×3–5.

## 0. Методология

Код изучен: `src/core/{horizon,dem,dem-source,geo,terrarium,peaks,db,skyline,
skyline-match,fft,orientation,dem-config,fetch-timeout}.ts`,
`src/workers/horizon.worker.ts`, `src/ui/{panorama,ar,map}.ts`,
`src/{main,sw}.ts`, `vite.sw.config.ts`, docs/STATUS, ALGORITHMS,
ARCHITECTURE, DATA-PIPELINE.

Помимо чтения кода, выполнены замеры на этой машине (desktop, x86-64, Node 22,
V8; телефонные оценки — умножением на 3.5, что соответствует наблюдению
«на телефоне в 3–5 раз медленнее»):

| Замер (1.93 млн шагов = 3600 лучей × 536 шагов) | Desktop |
|---|---|
| `makeRayMarcher.pointAt` (asin + atan2 + 2×нормализация) | **103 мс** |
| `computeLayeredHorizon` с дешёвым сэмплером (весь марш) | **218 мс** |
| то же с билинейной выборкой (синтетика дороже реальной) | **598 мс** |
| `filterVisiblePeaks`, 2000 синтетических пиков | 5 мс (ранний обрыв луча работает) |
| `buildRidgeSegments` 7 профилей × 3600 (пустые гребни, без `ctx`) | 2.0 мс |
| `silhouetteProfile` (до 13 массивов × 3600) | 1.6 мс |
| Холодный prefetch веера (Приют 11): уникальных тайлов Terrarium | **66** (z12=1, z11=6, z10=10, z9=49); prefetchNear +12 → ~78, ~2.5–3 МБ |

Проверенные данные: `peaks/elbrus.json` — 1600 вершин (0.19 МБ);
`peaks/iberia.json` — 49 167 вершин (4.84 МБ); `regions.json` — 48 КБ;
главный JS-чанк — 105 КБ, worker — 30 КБ; изоляция 49 тыс. вершин — 89 мс
(STATUS.md).

Все предложения с пометкой «побитово» сохраняют значения с точностью до
бита; «эквивалентно» — сохраняют вердикты (видимость, силуэт, порядок слоёв)
доказуемо; «визуально» — допустимы, но явно помечены.

## 1. Топ-5 по реальной тяжести

### №1. Сетевой путь первого расчёта: последовательные пробы индексов ×8 с + полный веер до первого марша

**Код.** `src/main.ts → initDemForRegion` вызывает `pickDemBase`
(`src/core/dem-config.ts`), который перебирает кандидатов **последовательно**:
`for (const candidate of candidates) { if (await probes.online(candidate)) … }`.
Проба — `fetchWithTimeout(url/index.json)` с таймаутом **8 с**
(`src/core/fetch-timeout.ts`, `FETCH_TIMEOUT_MS = 8_000`). Для hi-слоя и
пирамиды кандидатов по два (локальный + внешний Pages), для патча — один;
три `pickDemBase` идут параллельно (`Promise.all`), но внутри каждой цепочки
— строго по очереди.

**Что это значит для «мёртвой» сети в горах** (типичный сценарий, ради
которого и делался офлайн-режим):

- peaks: `main()` ждёт `fetchWithTimeout(peaks/{region}.json)` — **8 с**, только
  потом уходит в IndexedDB (`getPeaks`);
- пробы индексов: цепочка «локальный → внешний» для hi и global — до **2×8 = 16 с**
  (параллельные цепочки, берём максимум);
- в воркере `DemSource.init()` → `loadIndex()` каждого сэмплера тоже сначала
  идёт в сеть (8 с), потом в кешированный индекс — ещё **~8 с**;
- `compute()` ждёт `Promise.all(prefetchTasks)` **до первого шага марша**:
  веер 72×8 км + `prefetchNear` ≈ 78 уникальных тайлов Terrarium + тайлы
  патча/hi. При мёртвой сети каждый тайл висит до 8 с (все параллельно) —
  ещё **~8 с**.

Итого холодный запуск с тёплой IndexedDB при мёртвой сети: **~35–40 с до
первого кадра**, хотя все данные лежат на устройстве. При живой, но медленной
сети (EDGE/3G в горах, RTT 0.5–2 с): ~110–130 запросов через пул ~6 соединений
на origin → **5–20 с** только на доставку тайлов; SW на install одновременно
прекэшит **все** чанки приложения (`vite.sw.config.ts` кладёт в `PRECACHE`
весь `dist/assets/*.js|css`: карта, настройки, поиск, skyline…), соревнуясь за
те же 6 соединений.

**Почему это тяжело именно на слабом телефоне.** Не CPU — время. Каждая
проба и каждый тайл идут через `AbortSignal.timeout(8000)`, и последовательные
цепочки **умножают** таймаут на число кандидатов. На десктопе с хорошей сетью
это незаметно (пробы — десятки мс), в горах это главный тормоз запуска.

**Фиксы (все — «эквивалентно», выбор источников не меняется):**

1. **Параллелить кандидатов внутри `pickDemBase`**: запустить все пробы
   `Promise.all`, выбрать первый подошедший **по исходному порядку**
   (кандидаты независимы, преференс — по индексу). Время = максимум, а не
   сумма. Побитово тот же выбор: порядок приоритетов не трогается.
2. **Офлайн-быстрый путь**: если `navigator.onLine === false` — не ходить
   в сеть вовсе: пробы только `cached`, peaks только из IndexedDB, `loadIndex`
   только из кешированного индекса. `onLine=false` надёжен (в отличие от
   `true` при полуживой сети — но тот случай остаётся на таймаутах, это
   невозможно отличить без сигналов ОС).
3. **Короткий таймаут для проб**: проба `index.json` не должна делить
   таймаут с тайлами — 2–3 с достаточно, чтобы отличить «нет файла» (быстрый
   404) от «сеть не отвечает». Ложный промах на очень медленной сети не
   страшен: `cached`-проверка идёт следом и подхватывает кешированный индекс.
4. **SW: прекэш чанков не в install**, а по сообщению от страницы «первая
   панорама готова» (или в `requestIdleCallback`-эквиваленте SW — по таймеру
   после активации). Состав кеша тот же, момент наполнения другой:
   гарантия «настройки работают офлайн после первого онлайна» сохраняется,
   если страница успела отработать хоть раз (fallback — отложенный
   `cache.addAll` в `activate`, но запускать его только после сигнала или
   спустя N минут, а не в момент первого запуска).

**Ожидаемый эффект.** Мёртвая сеть: 35–40 с → **8–10 с** (остаётся один
неделимый цикл таймаутов, все параллельные). Медленная живая сеть: 5–20 с →
**2–6 с** (меньше конкуренция за пул соединений). Хорошая сеть: без изменений.

**Риск/сложность:** низкий/низкая. Нужны тесты на порядок выбора кандидатов
(`pickDemBase`) и на офлайн-путь (уже есть каркас в `dem.test.ts`).

### №2. AR и поворот: полный перерендер на каждое событие датчика + дублирующий рендер поверх AR-кадра

**Код.** `src/main.ts`: колбэк `orientationTracker.start(...)` вызывает
`draw()` при каждой эмиссии сенсорного состояния. `emitSensorState`
(`src/core/orientation.ts`) эмитит при сдвиге >0.1° **или не реже раза
в 100 мс даже в полном покое** (`now - this.lastEmitted > 100`). При повороте
— до 60 Гц (каждое событие `devicemotion`), без `requestAnimationFrame`-коалесцинга.
`pointermove` на десктопе зовёт `draw()` на каждое событие мыши (часто > 60 Гц).

В AR (`src/ui/ar.ts`) отдельный `requestAnimationFrame`-цикл рисует
`drawArFrame` каждый кадр: `drawImage` видео + **два** вызова `drawOverlay`
(контуры полупрозрачно, подписи непрозрачно). Но `draw()` в `main.ts`
**не знает про AR-сессию**: пока камера включена, каждое сенсорное событие
рисует полную панораму (градиент неба + гребни + подписи), которую через
миллисекунды затирает следующий AR-кадр. Это гарантированные 10 полных
лишних рендеров в секунду в покое и до 60 при движении.

Цена одного полного рендера (`renderPanorama` → `drawOverlay` +
`drawLabels`), на каждый кадр заново:

| Операция | Аллокации в кадре | Итерации |
|---|---|---|
| `buildRidgeSegments` × 7 профилей (`crests`) | объекты `{x,y}` на каждую точку | 7 × 3600 обходов + `wrapAngle` на точку |
| `strokeRidge` | — | до 14 × `ctx.stroke()` (7 слоёв × 2 цвета) |
| `runningMax` | `new Float32Array(3600).fill(−Inf)` | — |
| `silhouetteProfile` | `new Float32Array(3600)` | до 13 профилей × 3600 ≈ 47 тыс. |
| `drawLabels`: `tryPlace` | строки `labelText`, объекты `PlacedLabel` | `measureText` на каждого кандидата |
| `liftAboveSilhouette` (скрытые) | — | до 52 итераций × 5 чтений силуэта |
| `findPeakMarkerPosition` | — | окно фронтов ± rays на кандидата |
| `ctx.canvas.clientWidth` | — | **layout-read** на кадр (×2 в AR) |

Замеры дают нижнюю границу: сегментация 2 мс + `silhouetteProfile` 1.6 мс
на десктопе при **пустых** гребнях синтетики; с населёнными гребнями и
`measureText` (шейпинг шрифтов на Android — самое дорогое из всего списка,
0.1–1 мс на подпись) реальный кадр на телефоне оценивается в **15–40 мс JS +
GC-паузы**, не считая 14 `stroke()` и `drawImage` видео. Бюджет 16 мс
не выдерживается; GC-мусор (≈1 МБ/с молодых объектов только от
`silhouetteProfile` и сегментов) на слабом CPU даёт периодические фризы.

**Фиксы:**

1. **Не рисовать `draw()` при активном `arSession`** (AR-кадр всё равно
   перерисовывает всё в следующем rAF). Визуально тождественно: финальное
   состояние кадра то же. Риск ≈ 0. Тест в `main-module.test.ts`.
2. **Коалесцировать `draw()` через `requestAnimationFrame`** (флаг «запланировано»).
   Тождественно: рисуется финальное состояние за кадр.
3. **`silhouetteProfile` — кеш по версии панорамы.** Функция чистая от
   `state`, но `state` **мутируется на месте** (`Object.assign(panorama, next)`
   в `onmessage`), поэтому кеш — `{version, buffer}`, версию поднимать в том же
   `onmessage`. Побитово то же (47 тыс. итераций + аллокация уходят из кадра).
4. **Предрасчёт геометрии гребней в пространстве «индекс луча/угол»**
   (делается один раз на панораму, можно прямо в воркере): флаги «выше
   `runningMax` + EPS» и флаги разрывов (`MAX_RIDGE_SLOPE`) **не зависят от
   view** — зависят только от профилей. В кадре: проход только по видимым
   индексам `[iStart−2, iEnd+2]` (≈ fov/360° ≈ **1/5 лучей**), координаты —
   в переиспользуемый `Float32Array`. Эквивалентно: точки внутри кадра
   получают те же `x/y` (та же арифметика `azToX/elevToY`), точки за краем
   кадра и так отсекались `flush()`; шов 0° закрывается двумя диапазонами
   индексов (то же, что текущий `maxGap`-флаш).
5. **Кеш раскладки подписей.** Коллизии и порядок подписей **инвариантны
   к сдвигу `centerAzRad`** (вся сцена сдвигается целиком, `xToAz` сдвигается
   тем же центром); зависят только от `tilt`, FOV и кадра. Кешировать
   `placed[]` по `(версия панорамы, квантованный tilt, квантованный fov,
   локаль)`; стоящий человек в AR перестаёт пересчитывать layout каждый кадр.
   Тождественно при совпадении кванта. Отдельно — LRU-кеш `measureText` по
   `(текст, font, uiScale)`: текст подписи не меняется, пока не меняются
   вершины/локаль.
6. Микро: `uiScale` из `clientWidth` кешировать в `resize()` — убрать
   layout-read из кадрового пути.

**Ожидаемый эффект.** Кадр 15–40 мс → **4–8 мс** на слабом телефоне
(в AR — плюс `drawImage` видео, который остаётся); стабильные 60 fps вместо
10–30 fps при движении; GC-фризы уходят. Суммарно это главный вклад в цель
«кадр < 16 мс».

**Риск/сложность:** средний/средняя. Пункты 1–3 тривиальны; 4–5 требуют
аккуратности с инвалидацией кешей (мутация `panorama`!) — стеречь тестами
(`captions-layout.test.ts` расширить на инвариантность к `centerAz`).

### №3. Ядро марша: destination-тригонометрия, бининг слоёв в цикле, аллокации на луч, клонирование фронтов

**Код и замеры.** `computeLayeredHorizon` (`src/core/horizon.ts`):
1.93 млн итераций. Измерено на этой машине:

- `makeRayMarcher.pointAt` — **103 мс** (asin + atan2 + `toDeg` +
  `normalizeLon` с двумя `%` на шаг). Это ~47% «дешёвого» марша (218 мс);
- бининг слоя **внутри цикла шага**: `for (let b = 0; b < LAYER_COUNT; b++)`
  — до 6 сравнений на каждую из 1.93 млн итераций, хотя `bin` — функция
  только от `d`, то есть константа таблицы марша;
- на каждый луч аллоцируются 4×`Float64Array(5)` (`binMaxSlope`,
  `binDist`, `binMaxAngle`, `binExitSlope`) — 3600 × 4 = 14.4 тыс. массивов
  за расчёт (minor-GC в воркере на слабом CPU);
- результат пересылается в main: `horizon` — transferable, но
  `layers` (5×3600×4 = 72 КБ), `crests` (101 КБ), `distanceToHorizonM`
  (14 КБ) копируются, а `fronts` — **3600 массивов + тысячи объектов
  `VisibleFront`** — целиком structured-clone при каждом результате
  (оценка: 5–20 мс на телефоне на результат).

**Фиксы (все «побитово»):**

1. **`bin` — в таблицу марша** (`Uint8Array` рядом с `hints`): вычисляется
   теми же `LAYER_BOUNDS` один раз на 536 дистанций. Убирает до 6 сравнений
   × 1.93M из горячего цикла. Тождественно: `bin` — чистая функция `d`,
   последовательность `d` фиксирована.
2. **`normalizeLon` условной обёрткой.** В `pointAt`: `lon2 = lon1 + atan2(…)`,
   где `lon1 ∈ [−180, 180)`, `atan2 ∈ (−π, π]` ⇒ `|lon2| < 360`. Для
   `|x| < 360` цепочка
   `if (x > 180) x -= 360; else if (x < −180) x += 360;`
   (строгие сравнения — края 180/−180 сохраняются как есть) даёт
   **побитово тот же результат**, что текущий двойной `%`, но без модулей
   (ожидание: −15–25% от 103 мс).
3. **Переиспользовать буферы на луч** — один комплект `Float64Array(5)`
   снаружи цикла лучей; значения пишутся в слои после цикла луча.
   Тождественно.
4. **Трансфер всех буферов** (`postMessage(result, [horizon, layers…, crests…,
   distanceToHorizonM].map(b => b.buffer))`) и **фронты — SoA**
   (`Float32Array` четверок + `Uint32Array` оффсетов на луч, transferable)
   вместо 3600 массивов объектов. Числа те же, клонирование ≈ 0.
5. Мелочь на потом: слить quant-проход с delta-проходом в `decodeTile`
   (см. §4 — не в топ-5 сам по себе).

**Чего НЕ делать:** перестановка арифметики в `pointAt`
(`(1−sinLat1·A)·cosD − sinLat1·B·sinD` вместо `cosD − sinLat1·sin(lat2)`)
сэкономила бы ещё 10–20%, но нарушает побитовое равенство с `destination`
(существующий тест) — прирост не оправдывает потерю инварианта.

**Ожидаемый эффект.** Марш: 218 мс → **~170–180 мс** десктоп (−18–22%);
на телефоне −150–300 мс. Плюс исчезает пауза клонирования результата
(5–20 мс/результат). Это прямой вклад в цель «панорама < 500 мс», но без
№1 (сеть) и №4 (обрыв лучей) цель в худших случаях не достигается.

**Риск/сложность:** низкий/низкая. Тесты: «маркирующая функция совпадает
побитово» уже есть; добавить инвариант «профиль не изменился» (см. §5).

### №4. Ранний обрыв луча по верхней границе высоты (tileMax) и обрезка по покрытию

**Проверка кандидата из задания.** `tileMax` считается в `decodeTile`
(`src/core/dem.ts`), но не используется. Текущий обрыв
(`d > 60_000 && slope < binExitSlope[bin] && binMaxAngle[bin] < −0.005`)
для горного наблюдателя почти не срабатывает: на лучах к хребтам горизонт
положителен, `binMaxAngle < −0.005` ложно — марш идёт все 536 шагов.
Это подтверждает постановку вопроса.

**Что реально даёт tileMax (честный анализ).** Верхняя граница наклона
оставшегося пути: `B(d) = (H − hO − drop(d))/d`, где `H` — верхняя граница
высоты местности на оставшемся пути, `drop` — кривизна. Если `B(d) ≤ maxSlope`
и `B` дальше только убывает — оставшиеся шаги не изменят максимум, обрыв
**точен**. Монотонность: при `H > hO` функция `B` убывает всюду; при
`H ≤ hO` — при `d > d0 = √((hO−H)/k)`, `k = (1−0.13)/(2R) ≈ 6.83·10⁻⁸`.

Проблема — **какое H брать**:

- **Глобальный максимум по всем тайлам панорамы** — доказательство тривиально
  (любой не-NaN сэмпл лежит в предзагруженном тайле, иначе он бы не ответил),
  но граница почти бесполезна в целевом сценарии: на Приэльбрусье H ≈ 5642 м,
  наблюдатель ~3000–4100 м ⇒ `B(200 км) ≈ −0.0005…+0.008` — обрыв сработает
  только на лучах с уже очень низким горизонтом, то есть почти нигде.
- **Секторные границы** (max tileMax по сектору ±1–2 соседних) режут H в
  3–10 раз и реально помогают лучам в долины/море, но доказательство «всякий
  тайл луча задет веером сектора» ломается о случай, когда луч долго идёт
  параллельно границе тайла по «чужой» стороне от ближайшего веера
  (латеральный зазор 5° × d против 57 км тайла — зазор меньше тайла, но
  «сосед по диагонали» формально не покрыт). Это требует консервативного
  окаймления (брать тайлы с запасом в 1 тайл вокруг коридора веера) и
  отдельного доказательства, либо страховочного «переиграть без обрыва»
  при расхождении профиля с эталоном.

**Вывод по кандидату:** прежний аудит оценивал −20–40% шагов — это
оптимистично для сценария «наблюдатель высоко в горах». Реалистичная оценка
при секторной схеме с окаймлением: **−10–35%** шагов в альпийских сценариях
(обрываются лучи в низкие секторы на 120–170 км вместо 200), до **−60%**
на равнине/холмах (низкий наблюдатель, `H > hO` ⇒ `B` убывает всюду, обрыв
с ~150 км). Для Terrarium нужен `max` в `decodePng` (та же строка, где идёт
цикл декодирования — бесплатно).

**Обрезка по покрытию (второй кандидат из задания) — точная и дешёвая для
офлайна.** В офлайне с патчем региона лучи за bbox дают NaN на **всех**
оставшихся шагах (Terrarium недоступен, глобальная пирамида не тянется при
`fineAtOrigin`). Долгота вдоль луча постоянного азимута монотонна, широта
имеет не более одного экстремума ⇒ пересечение луча с lat/lon-bbox — не
более 2–3 интервалов дистанций. Найти последний шаг таблицы внутри bbox
можно грубым проходом (16–32 точки на луч, 3600 × 32 ≈ 115 тыс. вызовов
`destination` ≈ 6 мс) с локальным уточнением — и обрывать луч на нём.
Экономия в чистом офлайн-патче: **~64% шагов** (дальняя зона 30–200 км —
343 из 536 шагов) — это самый большой единичный выигрыш ядра, но только
в офлайн-сценарии.

**Ожидаемый эффект (оба механизма).** Онлайн/горы: −10–35% марша
(50–150 мс десктоп, 200–500 мс телефон); офлайн-патч: до −60% марша.
Риск: **средний** — корректность обрыва надо закрыть тестом «профиль
бит-в-бит не изменился» на реальных DEM-тайлах (см. §5) и аккуратным
доказательством окаймления.

### №5. Стартовый путь главного потока: peaks JSON.parse + annotateIsolation до первого compute

**Код.** `main()` последовательно: `getPosition` → `loadRegions` →
**await fetch + `res.json()` peaks** → **`annotateIsolation(peaks)`**
(синхронно, на главном потоке) → `initDemForRegion` → `requestCompute`.
Горизонт мог бы считаться **без вершин** — пики нужны только
`filterVisiblePeaks`.

**Почему тяжело.** `iberia.json` — 4.84 МБ, 49 167 вершин:
`JSON.parse` на телефоне ≈ 300–600 мс; `annotateIsolation`
(`src/core/peaks.ts`): сортировка 49 тыс. + сеточный поиск со строковыми
ключами `${cx},${cy}` в `Map` — 89 мс на десктопе, **~300–400 мс на телефоне**,
и всё это блокирует главный поток до первого кадра (и при каждой смене
региона). Для elbrus (1600 вершин, 0.19 МБ) — копейки, поэтому на дефолтном
регионе незаметно, но на половине регионов реестра — заметно.

**Фиксы:**

1. **Двухфазный расчёт.** Сразу после позиции слать воркер `compute` с
   `peaks: []` — панорама появляется на ~0.5–1 с раньше на больших регионах;
   когда peaks готовы — отдельное сообщение `peaks` (воркер переиспользует
   уже посчитанный `layered`, если origin тот же). Итоговый результат
   **эквивалентен** нынешнему: те же функции, те же входы, тот же порядок
   операций — видимость пиков не зависит от момента их прихода.
2. **`annotateIsolation` — в воркер**: peaks уходят сырыми, возвращается
   `isoM`-аннотированный массив (или целиком `VisiblePeak[]`). Главный поток
   освобождается; результаты для карты/поиска дождутся готовности.
3. **Кешировать изоляцию**: `isoM` зависит только от набора вершин региона —
   сохранять при `savePeaks` (кнопка скачивания региона) и при первом
   аннотировании в IDB; при старте читать готовое. (Детерминированность
   функции — аргумент корректности кеша.)
4. Опционально: `JSON.parse` peaks тоже в воркер (передать `Response`/
   `ArrayBuffer`), если останется боль в п. 1–3.

**Ожидаемый эффект.** Первый кадр на больших регионах: −0.5–1.0 с;
исчезает фриз главного потока на старте/при смене региона.

**Риск/сложность:** средний/средняя (протокол воркера, порядок сообщений,
защита от гонки смены региона — механизм `reqId`/`regionSwitchSeq` уже есть).

## 2. Проверка остальных кандидатов из задания (вердикты)

| Кандидат | Вердикт |
|---|---|
| **prefetch-веер 72×8 км + prefetchNear** | Замер: 66 уникальных тайлов Terrarium (~2.5–3 МБ), prefetchNear 27, из них 15 уже в веере (12 лишних, ~0.6 МБ); 65 тайлов задеваются >1 лучом, но дедупликация через `pending` работает — сеть качает только уникальные. Фикс «грузить грубый LOD только при нулевом бите покрытия» — побитово тот же результат, −30–50% патчевых запросов в разреженных пирамидах (hi-слой). |

| **drawOverlay/полилинии/подписи/clipToSilhouette/liftAboveSilhouette** | Покрыто №2 (кеши геометрии, силуэта и раскладки). |

| **Первый запуск: сколько МБ до панорамы** | Онлайн с нуля: оболочка + чанки (~0.2 МБ) + regions.json (48 КБ) + peaks (0.19–4.8 МБ) + 3× index.json (~десятки КБ) + **~78 тайлов Terrarium (~2.5–3 МБ)** + тайлы патча/hi (~1–2 МБ) ≈ **4–7 МБ, 110–130 запросов**. Всё, кроме оболочки/peaks, качается параллельно пулом ~6 соединений — отсюда 5–20 с на слабой сети (№1). |

| **Память** | STATUS.md, проблема 4: кеш тайлов в памяти не ограничен (Terrarium 262 КБ/тайл; после сессии блужданий — десятки МБ в воркере). На телефоне это GC-давление и риск OOM. Не скорость, но рядом: LRU с защитой тайлов активного расчёта. |

## 4. План измерений на реальном телефоне

**Фазовые метки в воркере** (`performance.mark/measure`, складывать в
результат — поле `timing: {…}` рядом с существующим `computeMs`):

```
prefetch-start → prefetch-done → march-start → march-done →
peaks-start → peaks-done → smooth-done → clone-done
```

Плюс счётчики: загружено тайлов (сеть/IDB/память), обрывов луча по каждому
правилу (текущее, tileMax, bbox), NaN-сэмплов.

**Метки в main:** `first-panorama` (от `navigationStart`/модуля до первого
`result`), `peaks-second-phase`; в AR — кольцевой буфер длин кадров
(среднее/p95/max за скользящую секунду, доля кадров >16.6 мс).

**Куда писать.** Без сервера — `localStorage` (кольцевой буфер последних
10 расчётов + агрегат за сессию, ключ `vershiny-perf`), выгрузка — кнопкой
«Скопировать диагностику» (JSON в буфер обмена) и/или в тот же txt, что
и снимок. Отдельно `performance.memory.usedJSHeapSize` (Chrome) до/после
10 поворотов на 360° — детект роста кеша тайлов и GC-фризов.

**Сценарии до/после (один телефон, 4–6 лет):**
1) холодный первый запуск онлайн (Wi-Fi); 2) холодный офлайн (регион скачан,
авиарежим); 3) повторный запуск (тёплый кеш); 4) AR 30 с неподвижно + поворот
на 360°; 5) шаг навипадом ×5 подряд (проверка очереди воркера); 6) смена
региона на «iberia» (путь peaks/изоляции). Для каждого: `first-panorama`,
фазы воркера, p95 кадра, GC-паузы.

**Регресс-защита «не побитово».** Закрепить эталон: прогнать
`computeLayeredHorizon` на зафиксированных DEM-тайлах (можно из тестовых
фикстур) и сохранить эталонные `Float32Array` профилей (horizon/layers/
crests) в репозиторий; после каждой оптимизации — сравнение бит-в-бит
в тесте (это же тест и для будущих правок марша). Для «визуальных» изменений
(если понадобятся) — сравнение максимума расхождения профилей с порогом
(например, 0.5·кванта высоты в угловом выражении).

## 5. Что сознательно не предлагается

WebGL/WASM/Rust, SAB-многопоточность, серверный рендер, фреймворки — по
ограничениям архитектуры. Многоворкерность с дублированием кеша тайлов —
отклонена: на телефоне два кеша Terrarium (≈20 МБ на панораму) съедят память
ради ~1.4× ядра, при том что №3+№4 дают сопоставимый выигрыш бесплатно.

## 6. Расхождения с предыдущим аудитом

(`docs/PERFORMANCE-AUDIT-FROM-Claude Sonnet 4.6.md`, не коммичен)

1. **tileMax (его №1)**: оценка «−20–40% шагов» завышена для горного
   наблюдателя — см. анализ в §4 этого документа; без секторного окаймления
   глобальная граница почти не обрывает лучи при наблюдателе ниже окружающих
   вершин. Реальная ставка — секторная схема с запасом + обрезка по bbox
   (офлайн), с тестом «профиль не изменился».
2. **filterVisiblePeaks (его №2)**: замер с 2000 пиками дал 5 мс (ранний
   обрыв луча пика уже в 876f9ab работает хорошо). Не в топ-5; дедупликация
   `distanceM`/`azimuthRad` — микро-правка, батч-предфильтрация с порогом 2°
   меняет `hiddenDeficitM` и классы на границе — «визуально», не побитово,
   выгода мала.
3. **Рендер (его №3)**: его цифры — нижняя граница (пустые гребни); реальный
   вес — `measureText` и GC. Его пункты А/Б/Г совпадают с моими №2.3–2.5;
   дополнительно найдено: **дублирующий `draw()` поверх AR-кадра** и
   **отсутствие rAF-коалесцинга** — они дают больше, чем все кеши вместе.
4. **Prefetch (его №4)**: подтверждено замером (66–78 тайлов, ~2.5–3 МБ);
   «прореживание по зуму» опасно (шаг веера привязан к размеру тайла z10,
   а не z9), безопасный вариант — coverage-aware отказ от грубых LOD
   (см. §2). Главный эффект — не CPU, а сеть (его №1 этого документа).
5. **decodeTile (его №5)**: перенос `*quant` в `cell()` — корректен и
   побитово эквивалентен (та же операция умножения, только позже), но это
   микрооптимизация (~5–10 мс телефона на холодный расчёт); включено как
   мелочь, не в топ-5.
