# Аудит AR-проекции (результат второй нейросети)

Аудит по промту PROMPT-AR-OPTICS-AUDIT. Главный вывод: самая крупная ошибка —
не «линейная вместо гномоники», а опорная точка проекции в AR — линия
0.62·H, а не оптическая ось кадра (0.5·H): 8.4° постоянного смещения, ~4°
прыжок при повороте телефона, до ~90 CSS-px бокового ухода при крене 20°.

**Статус реализации**: шаги A (опорная ось 0.5 + миграция калибровки),
B (несепарабельный API), C (pinhole по умолчанию, пиксельный порог кеша),
D (fl35 по диагонали кадра, zoom/`resizeMode`) и фаза B — LM-доводка
az/tilt/f со ступенью 3.5 (`core/calib-refine.ts`), мультигипотеза f и λ̂
с гейтом обусловленности — сделаны 2026-08-23. Очередь: применение λ̂ к
оверлею, живой AR с гистерезисом θ, якоря-вершины в кадре.

## Неточности (кратко)

| # | Неточность | Ошибка | Приоритет |
|---|---|---|---|
| 1 | HORIZON_FRAC=0.62 как опорная ось камеры (AR/фото) | 8.4° постоянно; 4.1° прыжок портрет↔ландшафт; 2.9° при крене 20° | критично |
| 2 | Анизотропия линейной модели (k_x ≠ k_y при tan-выводе FOV) | вертикаль пере-масштабирована на 14.6% у центра; до 60 px | критично |
| 3 | Крен вокруг центра холста при опоре 0.62 | 2·0.12·fovV·sin(ρ/2) | критично |
| 4 | Сепарабельность (x только от az, y только от elev) | 19–33 px для пика 10° над горизонтом у края | заметно |
| 5 | hfov = 2·atan(18/fl35) игнорирует пропорции кадра | 2.2–2.6° ≈ 3% масштаба | заметно |
| 6 | Кеш оверлея сдвигается translate'ом — под пинхолом до 148 px | блокер пинхола | блокер |
| 7 | zoom читается один раз, нормировка «1 = без зума» | до 2× масштаба | заметно |
| 8 | Нет resizeMode:"none", размеры из videoWidth | UA/EIS-кроп 5–12% FOV молча | заметно |
| 9 | λ нормирован по сырым пикселям | смена разрешения меняет смысл λ квадратично | до этапа 3 |
| 10 | angleToView с `!` — пинхол вернёт null за камерой | NaN на рисках 360° | блокер |
| 11 | xToAz на строке горизонта | выноски до ~10 px под пинхолом | косметика |
| 12 | Смена модели инвалидирует сохранённый cameraFovDeg | FOV «съедет» на 3–14% у существующих пользователей | критично при релизе |

## Решения аудита (принятые)

- **Шаг A** (без пинхола): опорная линия AR/фото = 0.5 (`OverlayOptions.horizonFrac`,
  `frameHorizonFrac`, фото-режим); панорама 360° остаётся на 0.62; миграция
  калибровки (version → сброс tiltDeg и cameraFovDeg при устаревании).
- **Шаг B**: несепарабельный API — `buildRidgeSegments`/`drawLabels` принимают
  `project(az, elev) → {x,y} | null`; шкала азимутов пропускает null.
- **Шаг C**: pinhole в AR/фото по умолчанию (λ≡0); порог дрейфа кеша и в
  покое, и в движении — пиксельный (`≤ ε/tan²(fovH/2)`); ручной drag считает
  разность углов по обеим точкам курсора; `CALIBRATION_VERSION=2` сбрасывает
  сохранённые линейные tilt/FOV; панорама навсегда линейная.
- **Шаг D** (выполнен 2026-08-23): fl35 → FOV по диагонали кадра;
  `resizeMode: "none"` + `track.getSettings()`; перечитка зума.
- **Позже**: LM-доводка (ступень 3.5), мультигипотеза по f, λ̂ с гейтом
  обусловленности (cond > 200 → λ̂ ≡ 0).

Детали (формулы, таблицы, план тестов) — в исходном тексте аудита и
docs/AR-PROJECTION.md.

## Шаг D: реализация (2026-08-23)

- **fl35 по диагонали кадра (№5)**: `diagFovFromFl35` / `longSideFovFromFl35`
  в `core/camera-fov.ts` — 35-мм эквивалент привязан к диагонали полного
  кадра 36×24 (43.27 мм), диагональный угол делится пропорционально
  сторонам ЭТОГО кадра (тангенс линеен по размеру на фокальной плоскости).
  Для 3:2 совпадает с прежней формулой 2·atan(18/fl35), для 4:3 длинная
  сторона на ~2.8% уже. Фото-режим (`main.ts` → `loadPhotoForAr`) считает
  FOV по размерам декодированного снимка (после EXIF-поворота).
- **`resizeMode: "none"` (№8)**: ограничение запроса камеры — UA не кропает
  кадр сенсора под EIS молча. Геометрия кадра для FOV (`fullFrameFov` в
  `ui/ar.ts`) берётся из `track.getSettings()` (фолбэк — размеры `<video>`):
  до первого кадра `videoWidth` = 0, и FOV считался бы по мусору.
- **Перечитка зума (№7)**: `readZoom()` вызывается при каждом возобновлении
  сессии и по событию `resize` элемента `<video>` (события смены зума в
  спецификации нет — resize единственная зацепка).
- **Остаточные риски**: UA, игнорирующий `resizeMode`, по-прежнему кропит —
  кроп не компенсируется (полевой тест); фото с fl35 ultra-wide (длинная
  сторона > 100°) зажимается калибровочным лимитом `fovMaxDeg=100` —
  честная деградация, пинхол-модель там и так на грани применимости.
- **Тесты**: `test/camera-fov.test.ts` — «fl35 → углы кадра» (3:2 ≡
  2·atan(18/fl35), 4:3 на 2.8% уже, портрет ≡ ландшафт, мусор → null).

## Фаза B: LM-доводка (реализована 2026-08-23, core/calib-refine.ts)

- θ = (dAz, dTilt, log fovH[, λ]) доводится Левенбергом–Марквардтом с лоссом
  Хьюбера (δ = 2.5 px кадра) по вертикальным ICP-невязкам «колонка силуэта ↔
  DEM-горизонт на азимуте колонки»; якобиан численный (центральные разности в
  шкалах параметров), приоры к старту ступени (σ_az 0.2, σ_tilt 0.1,
  σ_logF 2% при доверии к FOV / 20% без).
- **Поэтапная разморозка** az+tilt → +fovH → +λ; ступень принимается только
  при улучшении Хьюбер-RMS отложенной трети колонок >15% (абсолютный порог
  1e-4 рад при почти нулевой невязке). Проекция — та же, что у оверлея:
  pinhole в AR/фото, linear в 360° панораме.
- **Мультигипотеза f** (при недоверии к стартовому FOV): сетка hfov 20°…120°
  (лог-шаг 1.15×) по медиане модулей невязок + полировка Брентом по гладкой
  потере; гейт: разброс профиля кадра < ~0.3° → гипотезы не строятся (на
  ровном горизонте f не идентифицируем — любая метрика уводит наклон по
  вырожденному хребту tilt↔fovV).
- **λ̂** — третья ступень: только пинхол, hfov > 60°, валидные колонки в
  обеих крайних шестых, cond(JᵀWJ) ≤ 200 (гейт оценивается в доверенной
  стартовой точке, а не в оптимуме ступени 1 — там λ и az коллинеарны).
  λ пока НЕ применяется к оверлею — это следующий шаг вместе с живым AR.
- **RANSAC-lite**: пять азимутальных секторов; дикий сектор (медиана > 3×
  медианы остальных и > 2δ) маскируется, рефит принимается только при
  улучшении hold-out.
- **Интеграция**: каскад в `main.ts` — после ступени 1 (силуэт) и ступени 3
  (послойный, по выигравшему слою `SkylineMatch.layer`); NN-путь без доводки
  (контуры матчатся по слоям по отдельности). Принятый f обратным пересчётом
  зума (`ArSession.zoom`) ложится в `cameraFovDeg` и `syncFov()`; отказ
  ступени f оставляет калибровку как была.
- **Грабли, закрытые тестами**: приор наклона сильнее данных смещал оценку;
  насыщение ψ Хьюбера при стартах дальше ~0.3° удерживает параметры у старта
  (для робастного сдвига это свойство, а не баг — ступень 1 даёт старт в
  пределах линейного режима); гейт cond чувствителен к точке оценки.
- **Синтетика** (`test/calib-refine.test.ts`, 11 тестов): DEM-горизонт →
  «фото-силуэт» через ground-truth проекцию (линейную аналитически, пинхол —
  бинарным поиском азимута колонки), шум 0.5–1.5 px, облачные пропуски:
  восстановление az/tilt/f, мультигипотеза (58° при старте 70°), честный
  отказ ступени f на ровном горизонте, λ̂ ≈ 0 без дисторсии и λ̂ ≈ 2e-6 с
  ней, null при сплошных пропусках, бесшумная точность ±0.05°. Проверка:
  tsc 0, 658/658, build ок.
