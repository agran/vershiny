## Что уже рассмотрено и ОТКЛОНЕНО (не предлагай, причины — в `docs/CODE-REVIEW.md`)

- `Math.sin(lat2)` → `clamped` в марчере (`sin(asin(x))`): −38.9 % марчера, но
  `sin(asin(x)) ≠ x` на ~0.5 % точек (1 ulp), 4 точки из 1.93 млн пересекают
  границу пикселя → профиль меняется + ломает инвариант марчера.
- `atan(y/x)` вместо `atan2(y,x)`: гард `x > 0` съедает выигрыш, `x < 0`
  достижим на полюсах.
- Слитная константа `drop + hO` в таблице: 35 % значений slope отличаются на
  1 ulp.
- Обратное деление `(h−drop−hO)·(1/d)`: меняет последний бит slope.
- Инлайн `pointAt` без объекта: ломает сигнатуру `SampleFn` и инвариант.
- Пропуск марша пиков заведомо ниже горизонта: марш пика и слоистый марш идут
  по разным сеткам шагов — нужен маргин, классификация меняется в краях.
- LUT/аппроксимации тригонометрии в гео/марше: ломают битовый паритет.
- Агрессивнее RDP (`RIDGE_SIMPLIFY_PX > 0.5`): изменит контур.
- Ослабление порогов/штрафов skyline: изменит профиль и калибровку.
- Батч-предфильтр пиков 2°: меняет `hiddenDeficitM` и классы на границе.
- Прореживание prefetch-веера по зуму: ломает покрытие.
- Перестановка арифметики в `pointAt`: ломает побитовый паритет.
- Декодированные тайлы в IndexedDB вместо сжатых: ×3–4 места.
- Инлайн `lonLatToTileAndPixel` в `TerrariumSampler.sample`: медленнее (V8
  держит объект в регистрах).
- Гребни «только по видимым индексам»: потолок 0.69 мс/кадр, flush-семантика
  разрывов не совпадает с `buildRidgeSegments` при наивной реализации.
- Скользящее окно в `smoothLayers`: не побитово (порядок суммы) и <0.5 мс.
- Таблица twiddle вместо рекуррента в FFT: медленнее и не побитова.
- Числовой разбор ключа тайла в `sectorMaxHeights`: 0.05 мс на compute.
- Таблица Меркатора (`tan+sec+log`) по широте: проекция 1 раз на выборку,
  вклад ~3–5 % марша.
- Шардирование марша по воркерам: SAB упирается в COOP/COEP на Pages.
- Кеш «последний пиксель» для `pointAt`: меняет выборку на границах тайлов.
- `binExitSlope` алгеброй: выигрыш на уровне шума замера.
- Чтение `frontsFlat` без распаковки в объекты: ~0.3 мс.

## Инварианты, которые НЕЛЬЗЯ ломать

- `makeRayMarcher` обязан совпадать с `destination` **побитово** (тест-
  инвариант в `test/geo.test.ts`).
- Профили горизонта/слоёв — тесты сравнивают **бит-в-бит** (`toEqual` на
  Float32Array): оптимизации марша должны давать идентичный результат, иначе
  пиши, почему результат тождественен и какой тест это докажет.
- `sectorMaxHeights` и зонд покрытия — консервативные верхние границы: любая
  обрезка обязана не менять видимое (силуэт, горизонт, фронты).
- 569 тестов зелёные, `tsc` без ошибок, `npm run build` проходит.
- Стек не менять: без WebGL, без фреймворков, без сервера, без GPL-зависимостей;
  комментарии по-русски, идентификаторы по-английски.

## Методология: как доказывать и мерить

1. **Побитовость** — дифференциальный тест: встрой эталонную копию прежней
   логики в тест и сравни побитово (`toBe` / `Object.is`) на представительной
   сетке: случайные точки + границы тайлов + антимеридиан + полюса. Паттерн:
   `test/terrarium-fastpath.test.ts`, `test/dem-fastpath.test.ts`,
   `test/horizon-bound-diff.test.ts`, `test/panorama.test.ts` (сторож
   filter-эталона).
2. **Замер** — bench-скрипт в `tools/perf/` (`npx tsx`, Node 22, десктоп;
   телефон ≈ ×3.5): разгон + ≥3 итерации, полный проход (все лучи × шаги), а не
   фрагмент. Существующие: `bench-marcher`, `bench-sample`, `bench-ridge`,
   `bench-dem-fastpath`, `bench-sinasin`, `bench-profile-diff`.
3. **Для марша** — используй test-харнессы (синтетический сэмплер) или
   реальные тайлы.
4. **Финальная проверка** — `npm test`, `npx tsc`, `npm run build`.

## Ловушки (в которые упирались прошлые сессии)

- `NaN !== NaN` — «побитовое» сравнение пиши как
  `a !== b && !(Number.isNaN(a) && Number.isNaN(b))`.
- `toRad(x) = x * (Math.PI / 180)` НЕ тождественно `(x * Math.PI) / 180`
  (1 ulp) — в harness-копиях марчера используй `toRad`/`toDeg` из `geo.ts`,
  а не собственные конверсии.
- `normalizeLon(x)` не тождественна `x` даже внутри [−180, 180) (1-ulp сдвиг
  от цепочки остатков).
- `prettier --write` в этом репозитории реформатирует чужие строки
  (`panorama.ts` и соседи не в каноне) — проверяй `git diff --stat` после
  `--write`; при постороннем реформате — checkout файла и переприменить свои
  правки.
- Format-on-save пользователя реформатирует файлы параллельно с агентом —
  сверяй дифф перед коммитом.
- Vite на 404 отдаёт index.html (SPA-fallback) — проверяй Content-Type при
  fetch данных.
- Windows-консоль (cp1251) не выводит Unicode — в Python-скриптах:
  `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`.
- Приватные методы (`setTile`) вызывай как методы (с `this`), а не вытаскивая
  из объекта.
- Ручные точки «на границе тайла» через обратную проекцию могут из-за
  round-trip float попасть не в ту ветку (`py=0` ровно → 255.999): для
  interior бери `px=0.5/py=0.5`, для edge `px=255.5/py=255.5`.

## Что именно искать

- Повторные вычисления на шаг/луч: лишние вызовы функций, пересчёт констант в
  циклах, `Math.*` где хватает таблиц (таблица марша уже есть — ищи, что ещё
  таблицируемо).
- Вычисление до проверки: отсечения дешевле по оценкам сверху/снизу, прежде
  чем платить за точный расчёт.
- Арифметику с плавающей точкой: где допустимо переставить операции без
  изменения битов, где `x*x` вместо `pow`, где константу можно свернуть.
- Развёртки/сплайны: в каком месте предрасчёт «дешёвый при построении,
  дорогой на кадр» сдвигается в правильную сторону.
- Кеши, инвалидация: лишние перестроения буферов, layout-reads
  (`clientWidth` и т.п.), выделения Float32Array на кадр.
- Декод и выборка DEM/Terrarium: лишние проходы по 65 536 элементам,
  повторная распаковка, копирования буферов.
- `structuredClone`, спреды, `slice`/`subarray` копии в горячих путях.

## Формат каждой находки

1. Файл:строка, суть (2–3 предложения).
2. Математическое обоснование, почему результат не изменится (побитово /
   с погрешностью ≤ X; где X — обоснуй).
3. Реальный замер ДО и ПОСЛЕ (node-скрипт или `vitest bench` на
   представительном вводе), а не оценка на глаз. Для марша используй
   реальные тайлы из `public/tiles` или `test/`-харнессы.
4. Какой существующий тест стережёт инвариант и какой тест нужно добавить.
5. Оценка выигрыша (мс/кадр, % фазы) и риск.
