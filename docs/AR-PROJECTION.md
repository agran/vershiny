# Модель камеры для оверлея AR: план внедрения

**Статус**: этап 0 и шаги A–D аудита (docs/AR-OPTICS-AUDIT.md) выполнены.
AR/фото по умолчанию используют pinhole (λ≡0), с опорной осью 0.5,
несепарабельным API проекции и пиксельным порогом дрейфа кеша. Сохранённые
линейные tilt/FOV мигрируются сбросом версии калибровки. Реализованы fl35 по
диагонали кадра, `resizeMode: "none"`/`track.getSettings()`/перечитка зума,
LM-доводка и точный desktop-поиск по нескольким контурам; очередь —
применение λ̂ к оверлею и якоря-вершины в кадре.

## Проблема

Оверлей рисует контуры линейной проекцией (`x = Δaz/fov_H·W + W/2`), а реальное
фото после прошивочной коррекции — прямолинейное (гномоника,
`x = W/2·tan(Δaz)/tan(fov_H/2)`). Обе формулы совпадают в центре кадра и на
краях FOV, а между ними расходятся S-образно: на hfov=76° максимум ≈2.4°
азимута (~3% ширины) на ~0.6 полукадра, по вертикали ≈1.2°. Сдвигом az/tilt
остаток не поглощается. Дополнительно: номинальный FOV ≠ фактический (zoom,
кроп, cover-crop), остаточная дисторсия объектива, обратные пересчёты
размазаны по кодовой базе.

## 1. Выбор модели проекции

**База — честный пинхол через матрицу поворота, а не сепарабельный тангенс.**
Текущая формула (и её «гномоническая» замена `tan(Δaz)`) сепарабельна: x
зависит только от Δaz, y — только от elev. У реального пинхола при tilt ≠ 0
оси перемешиваются: горизонт в наклонённом кадре — не прямая, а гипербола,
и объекты у краёв «съезжают» по вертикали. Раз уж менять модель — менять на
правильную:

```
d = (cos e·sin Δa, sin e, cos e·cos Δa),   v = R_tilt·d,
x_n = v_x/v_z,  y_n = v_y/v_z
```

**Дисторсия — division-модель Фицгиббона с одним параметром λ**, а не
Brown k1,k2: `r_u = r_d/(1 + λ·r_d²)`. Причины:
- оба направления аналитические (обратный ход — прямая формула; прямой ход —
  корень квадратного уравнения, без итераций на 5 000 точек каждый кадр);
- один параметр оценивается по силуэту, два — вырождены почти всегда;
- одним параметром тянет и умеренный fish-eye.

**Нормировка λ — по пикселям кадра, не по f** (смысл не зависит от
pinch-зума, cover-кропа и поворота телефона).

**Fish-eye (FOV > ~115°)**: не пытаться. Детект — упор оценки hfov в верх
сетки поиска / EXIF LensModel / большая невязка после fit'а → честный отказ
от ступени дисторсии (остаётся линейная).

**Панорама 360° остаётся линейной** — правильное окно в цилиндр. **Крен
остаётся canvas-поворотом**: поворот вокруг оптической оси — в точности
поворот картинной плоскости вокруг главной точки.

Итого параметров: θ = (az₀, tilt, roll, log f, λ); roll из акселерометра,
реально оптимизируются 4.

## 2. Наблюдаемость по одному кадру

| Режим кадра | Что оценимо |
|---|---|
| Плоский горизонт (море, степь) | только tilt и roll → отказ от az/f/λ (`MIN_PROFILE_STD`) |
| Рельеф в узкой полосе кадра | az, tilt; f — плохо, λ — никак |
| Рельеф по ширине, но без краёв | az, tilt, f |
| Рельеф с признаками в крайних третях | + λ |

Ключевая вырожденность — **f против λ**: оба «масштабируют», различаются
только формой S-кривой. Разделяются при признаках минимум на двух
существенно разных радиусах от центра. Правило: **λ размораживается только
при hfov > ~60° И валидных колонках в обеих крайних шестых кадра.** При
hfov < 50° расхождение линейной и гномонической меньше шума экстракции —
λ ≡ 0 всегда. Вершины-якоря — лучшие ограничения (2D-точки рвут
вырожденность «симметричный профиль»).

## 3. Алгоритм оценки

**Фаза A — грубая (ступень 1, расширенная).** Круговая ZNCC как сейчас, но
при недоверии EXIF — **мультигипотеза по f**: сетка кандидатов hfov
(лог-шаг ~1.15×, 20°…120°, ~15 кандидатов; БПФ кольца один раз, на кандидата
— пересэмплинг + один БПФ ~1 мс).

**Фаза B — нелинейная доводка (новая ступень 3.5).** Левенберг–Марквардт по
θ с лоссом Хьюбера (δ ≈ 2–3 px·uiScale) над невязками: колонки силуэта
(вертикальный ICP «точка–кривая») + якоря-вершины (2D, бóльший вес).
- Якобиан численный (4–5 параметров × ~600 колонок × ~6 итераций — единицы
  миллисекунд в воркере).
- Оптимизировать log f; приоры-регуляризаторы к стартовым значениям
  (σ по качеству источника; λ прижат к 0) — автоматическая честная
  деградация без отдельных if.
- Поэтапная разморозка: (1) az+tilt → (2) +f → (3) +λ; каждая разморозка
  принимается только если RMS на отложенной трети колонок улучшился >15%
  (формальная гарантия «не хуже линейной»).
- RANSAC-lite по 5 азимутальным секторам: дикий сектор маскируется, рефит.
- Старт без EXIF: f — победитель мультигипотезы, az — ZNCC, tilt/roll — IMU,
  λ = 0.

## 4. Производительность

- Прямой ход на кадр: sin/cos азимутов 3600 лучей предвычислены; на точку —
  sin/cos(elev), умножение на R, деление, корень division-модели.
  ~0.2–0.5 мс на 5 000 точек — LUT не нужен на старте; мерить через `?perf`
  (фазы ridge/overlayTotal инструментированы).
- Обратный ход (drag, drift, экстракция, NN-фолбэк) — аналитический.
- Воркер: ZNCC-мультигипотеза и LM. Main thread: только прямой ход с
  готовым θ.
- Гистерезис: θ обновляется калибровочными событиями; экспоненциальное
  сглаживание + мёртвая зона ~0.3 px; λ между калибровками заморожен.

## 5. Единая цепочка координат

`core/camera-projection.ts`:

```
interface CameraProjection {
  angleToView(azRad, elevRad): {x, y} | null   // null = за камерой
  viewToAngle(x, y): {azRad, elevRad}
}
```

Цепочка кадра: мир (az,elev) → R(az₀,tilt) → гномоника → division(λ) →
пиксели полного кадра (f, центр) → cover-crop-аффинность (`camera-fov.ts`) →
view px; крен — canvas-поворотом. Две реализации: `LinearProjection`
(побитово ≡ прежним `azToX`/`elevToY`) и `PinholeProjection`. Панорама
всегда линейная; AR/фото всегда используют pinhole (λ≡0).
Экстракция профиля кадра обязана идти через `viewToAngle` (иначе ступень 1
получает смещённые углы у краёв), колонки кадра перестают быть равномерными
по азимуту — пересэмплинг на кольцо поколоночно.

## 6. План интеграции в каскад

1. **Этап 0 — чистый рефакторинг** [сделан 2026-08-23]: `CameraProjection`,
   все точки px↔угол переведены на `LinearProjection`; поведение бит-в-бит.
2. **Шаг A аудита** [сделан 2026-08-23]: опорная линия AR/фото = 0.5
   (`OverlayOptions.horizonFrac`, `AR_HORIZON_FRAC`), миграция калибровки
   (`CALIBRATION_VERSION` → сброс tilt/FOV).
3. **Шаг B аудита** [сделан 2026-08-23]: несепарабельный API —
   `buildRidgeSegments`/`drawLabels` принимают парный `toView`/проекцию,
   шкала азимутов пропускает null.
4. **Шаг C аудита** [сделан 2026-08-24]: pinhole в AR/фото по умолчанию
  (λ≡0); пиксельный порог дрейфа кеша действует и в покое, и в drag;
  ручная доводка берёт обе точки курсора из проекции видимого кадра;
  `CALIBRATION_VERSION=2` сбрасывает сохранённые линейные tilt/FOV.
5. **Шаг D аудита** [сделан 2026-08-23]: fl35 → FOV по диагонали/длинной стороне;
   zoom (перечитка) и `resizeMode: "none"` + `track.getSettings()`.
6. **LM-доводка (фаза B, ступень 3.5)** [сделан 2026-08-23]: `core/calib-refine.ts` —
   Левенберг–Марквардт по (az, tilt, log fovH[, λ]) с лоссом Хьюбера, поэтапная
   разморозка с приёмкой по отложенной трети колонок, мультигипотеза f при
   недоверии стартовому FOV (сетка 20°…120°, лог-шаг 1.15×, полировка Брентом),
   λ̂ с гейтом обусловленности (cond > 200 → λ ≡ 0, оценивается только в
   пинхоле, hfov > 60°, покрытие крайних шестых), RANSAC-lite по пяти
   азимутальным секторам. Встроен в каскад за ступенями 1 и 3; результат
   применяется с обновлением `cameraFovDeg` (обратный пересчёт зума).
7. **Точная desktop-доводка** [сделан 2026-08-24]: после ручного совмещения
  `photo-contours.ts` один раз извлекает из кадра Sobel-границы яркости и
  цветового вектора, их NMS-силу, раскладывает границы по восьми направлениям
  касательной и строит точные EDT. `classic-photo-align.worker.ts` в три
  прохода перебирает малое окно az/tilt/FOV/roll по видимым фронтам DEM,
  упакованным в transferable typed arrays. Фронты сведены в три дистанционные
  полосы (0.5–5, 5–40, 40–200 км); каждая нормирована отдельно и получает
  мягкий вес по фотоподдержке, а скрытые `layers` не участвуют. Skyline остаётся
  отдельным якорем, но его поколоночное качество из DP и согласие со стартовой
  ручной позой уменьшают глобальный вес в дымке. Фиксированный сектор кадра
  отложен под hold-out; результат не
  применяется при его ухудшении, только существенной регрессии полосы с
  реальной фотоподдержкой (`support >= 0.45`, более 25% и 1.5 px), минимуме
  на границе после recovery или confidence <0.55. Если минимум обычного окна
  достиг края по azimuth или FOV и две полосы подтверждены фото, worker один
  раз расширяет только эти оси и затем возвращает мелкую полировку. Главный поток остаётся
  отзывчивым;
  изменившийся во время поиска кадр тоже отменяет применение. Удачный результат
  в фото-режиме разрешает калибровочный экспорт: контуры и подписи запекаются,
  JSON с камерой, экранными пиками, hold-out и uniqueness пишется в PNG `iTXt`,
  имя получает `calibrated`.
8. **Очередь**: применение λ̂ к оверлею и живой AR с гистерезисом θ; якоря-
   вершины как 2D-ограничения (нужна разметка в кадре).

Ступени 1 (ZNCC), 2 (дип), 3 (послойный), 4 (NN) сохраняют роли — они дают
старт и соответствия, фаза B доводит.

## 7. Валидация и критерии приёмки

**Синтетика** (vitest, детерминированные сиды): горизонт из DEM → «фото-
силуэт» через ground-truth проекцию по матрице fov {30…120°} × λ
{−0.15…0.15} × покрытие {полное, полкадра, центр, доля плоского} + шум
экстракции σ=1–2 px и облачные пропуски.

**Реальный корпус**: S23 Ultra основная/ультраширик, iPhone, обрезанные/
отредактированные кадры; размеченные контрольные точки-вершины. Метрика —
ошибка в px по зонам радиуса (центр <0.3, середина 0.3–0.7, край >0.7
полудиагонали), медиана и p95.

Приёмка:
- синтетика при полном покрытии: fov <3%, az <0.2°, p95 в краевой зоне <1%
  ширины;
- корпус: p95 в краевой зоне на широких FOV улучшается ≥50% против линейной,
  и ни на одном кадре медиана не хуже линейной более чем на 0.5 px;
- вырожденные сцены: отказ ступени 100%, ложной уверенности ноль;
- `?perf`: overlayTotal ±0.5 мс от текущего.

## 8. Риски и честные отказы

| Риск | Мера |
|---|---|
| Вырожденность f–λ при узком покрытии | приоры + гейт краевых шестых + hold-out |
| Систематика экстракции силуэта (снег/облако) | невязки взвешивать надёжностью градиента; якоря-вершины как несмещённые опоры |
| Fish-eye/экшн-камеры | детект по упору hfov в край сетки → отказ от λ, линейный фолбэк |
| «Дыхание» оверлея в живом AR | θ только из калибровочных событий + мёртвая зона + λ заморожен |
| frameW/frameH врут при повороте устройства | цепочка питается frame-orientation-логикой, не сырыми track settings |

Отказ от ступени (остаёмся на текущем поведении): валидных колонок <40%
(`MIN_VALID_FRAC`), разброс профиля ниже порога, ZNCC-однозначность низкая,
hold-out хуже линейной, hfov-оценка на краю сетки.

**Резюме**: половина задачи — этап 0 (единый `CameraProjection` вместо
размазанных линейных формул); без него любая модель камеры разъедется на
обратных пересчётах точно так же, как линейная сейчас.
